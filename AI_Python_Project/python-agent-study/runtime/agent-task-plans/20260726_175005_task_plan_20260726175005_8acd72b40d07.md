# GitLab Agent 文档变更治理规范

## 1. 适用范围与角色职责

本规范适用于基于 GitLab Agent 的知识库文档发布流程，涵盖从文档修改、审核、合并到发布的完整生命周期。

### 角色定义

| 角色 | 职责 | 权限范围 |
|------|------|----------|
| Developer | 在功能分支修改文档并创建 Merge Request | 不得直接 Push 到 `main` 分支 |
| Maintainer | 审核 MR 内容、路径和权限规则，批准后合并 | 拥有 MR 审核和合并权限 |
| GitLab Sync Worker | 独立进程，从任务队列拉取 pending 任务并执行文档发布 | 仅通过任务队列获取待处理任务 |

---

## 2. 专用机器人账号隔离

> **注意**：机器人账号的具体配置细节（如账号名称、权限范围）需根据实际部署环境补充。

- GitLab Agent 应使用专用的机器人账号进行自动化操作，该账号与人工账号严格隔离。
- 机器人账号仅具备必要的最小权限，不得拥有直接 Push 到保护分支的权限（具体权限范围需根据实际部署环境配置）。
- 机器人账号的操作日志应单独归档，便于审计追踪。

---

## 3. 临时分支命名规范

Developer 必须从 `main` 分支创建临时特性分支进行文档修改，分支命名应遵循以下规范：

- 格式：`feature/<简短描述>` 或 `docs/<简短描述>`
- 示例：`feature/update-api-docs`、`docs/add-deployment-guide`
- 分支创建后，所有修改应在该分支上进行，完成后提交 Merge Request 到 `main` 分支。

---

## 4. 基于 last_commit_id 的乐观并发机制

系统通过以下机制保证并发更新的一致性：

- **publication_version**：全局版本号字段（存储于 PostgreSQL 或 Redis），每次成功发布后递增，确保版本一致性。
- **last_commit_id**：发布时记录对应的 Git commit SHA，用于追溯和回滚。
- **乐观并发控制**：通过版本号控制并发更新，防止多个 Worker 同时处理同一任务导致数据不一致。

---

## 5. Merge Request 人工审核流程

MR 必须经过 Maintainer 人工审核后方可合并，审核内容包括：

1. **内容准确性**：文档内容与技术事实一致，无错误信息。
2. **格式与结构**：符合 Markdown 规范，标题层级清晰，代码块正确标注语言类型。
3. **敏感信息检查**：确认无密钥、密码、内部地址等敏感数据泄露。
4. **路径合规性**：文档存放路径符合项目目录结构规范。
5. **权限规则**：文档的访问控制设置符合安全要求。

MR 必须至少由 1 名 Maintainer 审核批准后方可合并。

---

## 6. main 保护分支配置

GitLab 项目中 `main` 分支已启用保护（配置路径：Settings → Repository → Protected Branches），具体配置如下：

- **禁止直接 Push**：任何用户（包括 Maintainer）不得直接 Push 到 `main` 分支。
- **强制 MR 合并**：所有变更必须通过 Merge Request 流程合并。
- **审核要求**：MR 必须经过至少 1 名 Maintainer 审核批准。

---

## 7. 合并后 Webhook 与独立 Worker 同步机制

### Webhook 配置

- GitLab Webhook 触发事件为 `Merge events`（MR 合并到 main 时触发）。
- Webhook 接收端快速返回 `202 Accepted`，只登记或合并待处理任务，不直接处理文档发布。
- > **注意**：Webhook Secret 的具体配置和管理方式需根据实际部署环境补充。

### 独立 Worker 处理

- 文档发布由独立 Worker 进程执行，与 Webhook 服务分离部署。
- Worker 职责包括：
  - 从任务队列拉取 pending 任务
  - 拉取对应 commit 的文档内容
  - 校验权限规则
  - 写入 Elasticsearch/Milvus 等存储
- **原子性保证**：独立 Worker 必须把本次 Commit 的所有文档作为同一候选版本处理；任一存储写入或校验失败时不得部分提交，应整体回滚并记录错误日志。
- > **注意**：独立 Worker 的重试机制和超时策略需根据实际部署环境配置。

---

## 8. publication_version 原子发布

每次成功发布后，系统执行以下原子操作：

1. 递增 `publication_version` 字段值。
2. 更新 `last_commit_id` 为当前合并的 commit SHA。
3. 记录发布时间、操作人等信息（具体存储结构需根据实际部署环境配置）。

SQL 示例：
```sql
UPDATE system_config 
SET publication_version = publication_version + 1, 
    last_commit_id = '<commit_sha>', 
    updated_at = NOW() 
WHERE id = 1;
```

## 9. 审计要求

发布记录需归档，包含以下信息：

- commit SHA
- 发布时间
- 操作人（Maintainer 账号）
- publication_version
- 涉及的文档列表

归档日志应长期保存，便于后续审计和问题追溯。

## 10. 异常回滚流程

### 手动回滚

支持手动回滚到指定历史版本，通过 SQL 更新 `publication_version` 字段实现：

```sql
UPDATE system_config 
SET publication_version = <N>, 
    updated_at = NOW() 
WHERE id = 1;
```

其中 `<N>` 为目标历史版本号。

### 常见异常处理

| 异常场景 | 处理方式 |
|----------|----------|
| Webhook 未收到 | 检查 GitLab Webhook 配置、网络连通性、服务日志 |
| 任务长时间未处理 | 检查 Worker 状态、任务队列积压情况 |
| 发布失败 | 记录错误日志，支持重新触发或手动回滚 |
