### sq_2 - 知识库中以及 什么不应该在 Anim Notify 中决定最终伤害的核心设计是什么？

- 状态: `partial`
- 使用工具: `knowledge_retrieval`

根据知识库，不应该在 Anim Notify 中决定最终伤害的核心设计原则是**职责单一（职责分离）**。动画层仅负责视觉表现和发送时间点事件，而不应直接决定最终伤害数值 [chunk_b4c89e5d0b92dfee] [chunk_289996c1f6f37506]。

**不应该在 Anim Notify 中决定最终伤害的原因（风险与后果）：**
将攻击伤害等逻辑放在动画蓝图或 Anim Notify 中会导致以下问题 [chunk_03c6e8091066457e]：
1. **网络结果不稳定**：会导致网络同步时出现不稳定现象。
2. **动画资源变化影响战斗逻辑**：动画资源的修改会直接干扰或破坏战斗逻辑。
3. **自动化测试困难**：动画与逻辑高度耦合，导致难以进行独立的自动化测试。
4. **动画与程序相互锁死**：逻辑与动画绑定会使得程序和美术资源相互制约，难以维护。

**正确的设计方案：**
* **Anim Notify 的职责**：只负责发出攻击时间点事件，例如开始/结束武器 Trace、打开/关闭连招输入窗口、触发脚步音效和非关键 VFX 等 [chunk_289996c1f6f37506] [chunk_03c6e8091066457e] [chunk_a17565f13e822fca]。
* **最终伤害的结算**：最终伤害必须由**服务端权威的伤害计算模块**（或独立的伤害计算服务 / GAS Execution Calculation）结合攻击者与目标属性快照、技能/武器配置、命中部位、防御状态等统一结算 [chunk_03c6e8091066457e] [chunk_8edfd9c2c359d3eb]。

**二、 结构化报告：模块设计、关系和差异**

*注：由于子问题3（系统职责比较）未完成且证据不足，本报告中的职责比较部分仅能基于现有部分证据进行有限整合。*

**1. 模块设计**
* **输入与决策模块（客户端）**：包含输入缓存窗口（建议 0.18～0.28 秒），由 `Montage Notify State` 控制开启与关闭，作为客户端本地数据处理玩家输入。
* **动画协调模块（表现层）**：包含 Anim Notify，遵循职责单一原则，仅负责发送时间点事件（如武器 Trace、输入窗口开关、音效和 VFX），不处理核心战斗逻辑。
* **伤害结算模块（服务端权威）**：独立的伤害计算服务，负责接收事件和命中候选，结合属性快照等计算最终伤害。

**2. 模块关系**
* **事件驱动**：Anim Notify 在动画播放到特定时间点时发出事件，驱动输入模块（如打开连招输入窗口）和伤害结算模块的后续流程。
* **数据流向**：客户端输入模块收集输入缓存 -> 动画模块触发事件 -> 服务端伤害计算模块进行权威结算。

**3. 模块差异与职责边界**
* **输入缓存 vs 伤害计算**：输入缓存是客户端本地数据，用于优化操作手感；伤害计算是服务端权威逻辑，用于保证公平和防作弊（客户端仅提交动作和命中候选，服务器重新验证并计算最终结果）[chunk_afdf11b82350e6d7]。
* **动画表现 vs 核心逻辑**：Anim Notify 严格限制在视觉表现和时间点事件触发，严禁直接决定最终伤害，以避免网络不稳定、逻辑与动画锁死等问题。
