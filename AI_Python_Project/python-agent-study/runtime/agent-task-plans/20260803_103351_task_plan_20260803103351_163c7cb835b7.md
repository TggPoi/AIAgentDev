## Final Synthesis

在 PostgreSQL 16 中，RLS 与 `security_invoker` 视图解决的问题、配合方式及适用边界如下：

### 1. 分别解决什么问题
* **RLS（行级安全）**：主要用于在标准 SQL 权限系统之外，实现行级别的数据隔离与访问控制。它解决的是“合法查询访问了不该看的行”的安全问题，能够基于每个用户精细地限制正常查询返回的行，以及数据修改命令（INSERT、UPDATE、DELETE）可操作的行 [web_a58b98b7b96ce85f]。
* **`security_invoker` 视图**：解决的是默认视图（`security_definer` 上下文）下 RLS 被绕过的安全问题。默认情况下，视图使用视图所有者的权限检测底层对象，而表所有者通常不受 RLS 约束，这会导致通过默认视图查询时 RLS 行级过滤失效。`security_invoker` 视图通过以调用者（invoker）的权限执行，解决了这一数据越权访问问题 [web_454141d3e7a236e9]。

### 2. 如何配合
在启用了 RLS 的基表上创建视图时，**必须配合使用 `security_invoker` 选项**。
视图本身只是重写查询的语法糖，不改变权限检查的时机或层级 [web_3a0f9030b3aaef4b]。当视图被设置为 `security_invoker` 时，系统会以实际调用者的身份进行权限检查和 RLS 策略评估，确保调用者只能看到 RLS 策略允许其访问的数据行，从而保证 RLS 策略严格基于调用者身份生效 [web_454141d3e7a236e9]。

### 3. 适用边界
基于检索上下文中的官方网页证据，两者的适用边界如下：
* **RLS 的豁免与例外边界**：表的所有者（owner）通常不受 RLS 策略约束；此外，作用于整个表的操作（如 `TRUNCATE` 和 `REFERENCES`）也不受 RLS 限制 [mcp__fetch_ce37ee621cfc2df4]。
* **视图与 RLS 配合的机制边界**：无论是否使用 `security_invoker`，对启用 RLS 的基表所创建的视图执行 `SELECT` 时，都会完整评估基表上的所有 RLS 策略。`security_invoker` 的核心作用仅在于决定“以谁的身份”去触发和接受这些策略的评估，它并不能改变或绕过 RLS 策略本身的底层评估逻辑 [web_3a0f9030b3aaef4b]。

### 4. 限制与未解决项说明
* **部分满足与限制**：关于 `security_invoker` 视图更详细的适用边界（例如在复杂查询场景下的性能开销、特定数据类型下的具体限制等），当前知识库中没有足够信息回答（对应子问题 sq_2 和 sq_4 的检索结果）。上述适用边界仅基于 RLS 自身的豁免规则以及视图作为语法糖的底层机制得出。
