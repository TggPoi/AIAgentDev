## Final Synthesis

根据检索上下文，PostgreSQL 16 中 RLS 与 `security_invoker` 视图的比较、配合及适用边界如下：

### 1. 分别解决什么问题
* **RLS（Row-Level Security）**：解决在 SQL 标准权限系统（GRANT）之外的**细粒度行级数据访问控制**问题。它可以基于每个用户限制普通查询能够返回的行，以及数据修改命令（INSERT、UPDATE、DELETE）能够操作的行。当在表上启用 RLS 后，如果没有匹配的策略，则使用默认拒绝策略（来源：https://www.postgresql.org/docs/16/ddl-rowsecurity.html ）。
* **`security_invoker` 视图**：解决**视图权限检测主体**问题。它允许视图以调用者（invoker）的权限来执行和检测权限，而不是视图创建者的权限（来源：https://www.modb.pro/db/411528 ）。此外，在 PG 16.5 中，它还用于修复 RLS 场景下的缓存计划漏洞，确保在引用带有 RLS 策略的表时，系统能正确将缓存计划标记为依赖于“调用角色”（来源：https://www.postgresql.org/docs/16/release-16-5.html ）。

### 2. 如何配合使用
* **权限与策略的一致性评估**：当使用 `security_invoker` 视图查询启用了 RLS 的基表时，视图的权限检查和基表的 RLS 策略评估都会严格基于**调用者（当前用户）** 的身份进行。这确保了在视图层面和基表层面都能正确应用调用者的行级安全策略，防止因视图所有者权限过高而导致 RLS 策略被绕过或评估错误（来源：https://www.modb.pro/db/411528 ，https://www.postgresql.org/docs/16/release-16-5.html ）。
* **视图不绕过 RLS**：视图只是重写查询的语法糖，对启用了 RLS 的基表创建的视图，在执行查询时仍会完整评估基表上的所有 RLS 策略，不改变权限检查的时机或层级（来源：https://www.php.cn/faq/2689046.html ）。

### 3. 适用边界（基于官方网页证据）
* **RLS 的适用边界**：根据 PostgreSQL 16 官方文档，RLS 的边界在于行级访问控制。在表上启用 RLS 后，所有对表的正常访问都必须被行安全策略允许；如果不存在匹配的策略，则使用默认拒绝（default-deny）策略，即没有行可见或可被修改（来源：https://www.postgresql.org/docs/16/ddl-rowsecurity.html ）。
* **`security_invoker` 视图在 RLS 场景下的适用边界**：根据 PostgreSQL 16.5 官方发行说明，当查询中的 CTE、子查询、子链接或 `security invoker view` 引用了带有 RLS 策略的表时，必须确保系统正确将缓存计划标记为依赖于“调用角色（calling role）”。如果未能正确处理此依赖边界，可能会导致错误地返回或隐藏行（CVE-2024-10976）（来源：https://www.postgresql.org/docs/16/release-16-5.html ）。
* **架构设计边界**：在实际应用中，应让视图作为查询入口，而将真正的行级隔离逻辑交由基表的 RLS 独立生效。不要在视图里硬编码过滤条件（如 `WHERE user_id = ...`）来做“伪过滤”替代 RLS，因为应用可能会绕过视图直接查询基表，且视图定义无法动态响应会话变量变更（来源：https://www.php.cn/faq/2689046.html ）。
