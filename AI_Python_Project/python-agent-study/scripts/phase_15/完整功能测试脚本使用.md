## 15-7 Agent tool 完整流程测试

当前脚本已扩展为三种用法：

```text
1. 创建/更新 PostgreSQL 测试用户。
2. 使用测试用户交互式登录并测试多轮 RAG Agent。
3. 自动执行 15-7 工具权限完整流程：
   /auth/login
   -> /auth/me
   -> /rag/chat 生成工具执行确认单
   -> 错误 confirmation_text 拒绝
   -> 正确 confirmation_text 执行
   -> 校验本地测试文件创建、修改、删除结果
```

### 1. 创建 15-7 测试用户

脚本会直接写 PostgreSQL，创建或更新下面这些可登录用户：

```text
tool_reader    / Reader123456!   development / department_reader
tool_editor    / Editor123456!   development / department_editor
tool_manager   / Manager123456!  development / department_document_manager
tool_admin     / Admin123456!    system_admin
tool_unscoped  / Unscoped123456! development，但不绑定文档工具角色
```

这些账号的权限含义如下：

| 账号 | 密码 | 认证身份 | 部门范围 | 工具角色 | 能生成执行确认单 吗 | 能确认执行吗 | 建议测试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `tool_reader` | `Reader123456!` | 普通用户 | `development` | `department_reader` | 不能生成 create/update/delete approval | 不能 | 验证只读用户修改文档会被拒绝，且 `tool_confirmation_required=false` |
| `tool_editor` | `Editor123456!` | 普通用户 | `development` | `department_editor` | 只能生成 update approval | 不能确认执行，因为没有 `knowledge:document:approve` | 验证“可发起修改approval，但不能执行 approval” |
| `tool_manager` | `Manager123456!` | 普通用户 | `development` | `department_document_manager` | 可以生成 create/update/delete approval | 可以确认执行本部门 approval | 主测试账号，用它测试新增、修改、删除完整闭环 |
| `tool_admin` | `Admin123456!` | `admin` | `development` | `system_admin` 全局角色 | 可以跨部门生成执行确认单 | 可以确认执行 | 验证管理员路径和跨部门管理能力 |
| `tool_unscoped` | `Unscoped123456!` | 普通用户 | `development` | 无 15-7 工具角色 | 不能生成文档工具执行确认单 | 不能 | 验证“有部门但没有工具角色”仍被拒绝 |

这里要区分两层权限：

```text
user_departments：
    决定用户能检索哪些部门文档。

user_department_roles / user_roles：
    决定用户能不能调用 Agent 文档管理工具，以及能不能确认执行 approval。
```

执行：

```powershell
.\.venv\Scripts\python.exe scripts\phase_15\test_rag_agent_login_multiturn_cli.py `
  --seed-15-7-tool-users `
  --print-15-7-tool-users
```

这一步会补齐：

```text
users
user_departments
user_department_roles
user_roles
```

注意：`create_auth_user.py` 只能创建用户和部门，不能绑定 15-7 的 `user_department_roles`。所以测试 Agent tool 权限时，优先使用本脚本的 `--seed-15-7-tool-users`。

### 2.1 Agent 多步骤 TaskPlan 人工验收

当前 15-7 已经具备最小版 LLM 多步骤任务计划闭环。验收这个链路时，推荐使用 `tool_manager`，并使用下面这种表达，避免 Prompt Guard hybrid 模式把“查询知识库并保存”误判成 Prompt Injection：



### 3. 旧单工具自动流程已废弃

`--run-15-7-tool-flow` 对应的是旧的“自然语言 create/update/delete 单工具 approval”验收脚本。当前代码已经删除 `AgentDocumentActionPlanner` 入口，RAG Agent 不再把普通自然语言文档动作直接转换成单工具 approval。

不要再把下面这类输入作为 15-7 主验收项：

```text
请创建 development/x.md，内容是……
请更新 development/x.md，内容是……
请删除 development/x.md
```

这类输入应回到普通 RAG / direct answer，或因为不属于白名单 TaskPlan 而不产生 `agent_task_plan_id`、`tool_approval_id`。

### 4. 非流式接口：手工测试 TaskPlan approval 和确认

如果你想自己观察 approval 生成后的人工确认环节，使用 `--manual-confirm-tool-approvals`。

这个参数的含义是：

```text
1. CLI 调用 /rag/chat。
2. 如果响应里有 tool_approval_id，说明 TaskPlan 的高风险文档创建步骤已经生成 approval。
3. 人工检查 runtime/agent-tool-approvals/ 下对应 Markdown / JSON。
4. 确认无误后调用 POST /agent/tool-approvals/{approval_id}/confirm。
5. 未确认时 approval 保持 pending_confirmation，源文件不会写入。
```

注意：后端仍然校验完整 `confirmation_text`。CLI 的 `true` 只是本地人机确认按钮，不能绕过后端确认文本校验。

manager 用户是最适合手工测试 create / update / delete 的账号：

```powershell

  --base-url "http://127.0.0.1:8000" `
  --username "tool_manager" `
  --password "Manager123456!" `
  --mode hybrid `
  --top-k 5 `
  --candidate-k 10 `
  --manual-confirm-tool-approvals
```

启动后输入：

```text
请创建 development/manual-cli-test.md，内容是：# manual test
```

预期：

```text
1. CLI 打印 answer。
2. answer 中能看到 approval_id、markdown_path、json_path、confirmation_text。
3. CLI 打印 detected_tool_approval_id=...
4. CLI 提示 confirm true?>。
```

### 5. 结构化流式接口测试

结构化流式接口使用 `/rag/chat/stream/events`。它是 React 前端主线，不是 legacy token-only stream。

启动命令：

```powershell
.\.venv\Scripts\python.exe scripts\phase_15\test_rag_agent_login_multiturn_cli.py `
  --base-url "http://127.0.0.1:8000" `
  --username "tool_manager" `
  --password "Manager123456!" `
  --stream-events `
  --show-stream-events `
  --manual-confirm-tool-approvals
```

先输入普通 RAG 问题：

```text
RAG 后端部署步骤是什么？
```

预期结构化流式接口会打印：

```text
[event=sources]
source_count=...

[event=answer_delta] 或 guard_sanitized / guard_blocked
...

[event=done]
stream_done=passed
```

再输入工具计划请求：

```text
请创建 development/manual-stream-test.md，内容是：# stream manual test
```

预期：

```text
[event=tool_approval_created]
能看到 approval_id、markdown_path、json_path、operation、target_path、risk_level。

[event=tool_confirmation_required]
能看到 confirm_endpoint=/agent/tool-approvals/{approval_id}/confirm。

后续 answer_delta 中会输出包含 confirmation_text 的提示文本。
如果启用了 --manual-confirm-tool-approvals，CLI 会提示 confirm true?>。
输入 true 后调用确认接口并执行。
```

结构化流式测试重点不是看最终回答质量，而是确认：

```text
1. /rag/chat/stream/events 能输出 tool_approval_created。
2. 能输出 tool_confirmation_required。
3. 普通 sources / answer_delta / done 事件仍正常。
4. 工具执行仍然必须经过确认接口。
```

legacy `/rag/chat/stream` 仍是 token-only 兼容接口。这个 CLI 不把新的工具执行确认单测试放到 legacy stream 上；15-7 的前端主线应使用 `/rag/chat/stream/events`。
