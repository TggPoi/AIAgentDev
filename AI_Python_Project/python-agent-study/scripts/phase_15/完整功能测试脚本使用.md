## 15-7 Agent TaskPlan 测试

当前脚本支持三种用法：

```text
1. 创建/更新 PostgreSQL 测试用户。
2. 使用测试用户交互式登录并测试多轮 RAG Agent。
3. 使用 `--manual-confirm-task-plans` 手工确认 TaskPlan 写入。
```

### 1. 创建 15-7 测试用户

脚本会直接写 PostgreSQL，创建或更新下面这些可登录用户：

```text
tool_reader    / Reader123456!   development / department_reader
tool_editor    / Editor123456!   development / department_editor
tool_manager   / Manager123456!  development / department_document_manager
tool_admin     / Admin123456!    system_admin
tool_unscoped  / Unscoped123456! development，但不绑定文档工具角色
```

这些账号的权限含义如下：

| 账号 | 密码 | 认证身份 | 部门范围 | 工具角色 | 能生成 TaskPlan 吗 | 能确认执行吗 | 建议测试 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `tool_reader` | `Reader123456!` | 普通用户 | `development` | `department_reader` | 不能生成可执行写入 TaskPlan | 不能 | 验证只读用户写入任务被拒绝 |
| `tool_editor` | `Editor123456!` | 普通用户 | `development` | `department_editor` | 不适合 create 报告任务 | 不能确认 create | 验证权限不足路径 |
| `tool_manager` | `Manager123456!` | 普通用户 | `development` | `department_document_manager` | 可以 | 可以确认本部门 TaskPlan | 主测试账号 |
| `tool_admin` | `Admin123456!` | `admin` | `development` | `system_admin` 全局角色 | 可以 | 可以确认 | 验证管理员路径 |
| `tool_unscoped` | `Unscoped123456!` | 普通用户 | `development` | 无 15-7 工具角色 | 不能 | 不能 | 验证“有部门但没有工具角色”仍被拒绝 |

这里要区分两层权限：

```text
user_departments：
    决定用户能检索哪些部门文档。

user_department_roles / user_roles：
    决定用户能不能调用 Agent 文档管理工具，以及能不能确认执行 TaskPlan。
```

执行：

```powershell
.\.venv\Scripts\python.exe scripts\phase_15\test_rag_agent_login_multiturn_cli.py `
  --seed-15-7-tool-users `
  --print-15-7-tool-users
```

这一步会补齐：

```text
users
user_departments
user_department_roles
user_roles
```

注意：`create_auth_user.py` 只能创建用户和部门，不能绑定 15-7 的 `user_department_roles`。所以测试 Agent tool 权限时，优先使用本脚本的 `--seed-15-7-tool-users`。

### 2. 启动服务前确认环境

普通多轮 RAG 登录测试至少需要：

```env
AUTH_ENABLED=true
RAG_PIPELINE_PROVIDER=rag_agent
```

如果要确认 TaskPlan 后真实写入，还需要用下面配置启动 FastAPI：

```env
AGENT_DOCUMENT_TOOLS_ENABLED=true
AGENT_DOCUMENT_TOOLS_DRY_RUN_ONLY=false
AGENT_DOCUMENT_TOOLS_REQUIRE_CONFIRMATION=true
AGENT_MAX_TOOL_CALLS=12
AGENT_MAX_PARALLEL_TOOL_CALLS=4
KNOWLEDGE_BASE_DIR=docs/knowledge-base-acl-test
```

`AGENT_MAX_TOOL_CALLS` 是整个任务的调用总预算，失败和重试也计数；
`AGENT_MAX_PARALLEL_TOOL_CALLS` 是单轮最多并行执行的只读工具数。
有依赖的工具必须等待上一轮 ToolMessage，MCP、文档 dry-run 和 confirm 真实写入保持串行。

`AGENT_DOCUMENT_ACTION_PLANNER_MODE` 已废弃。文档动作不再由 Planner JSON 映射，15-7 主验收项改为原生 LLM Tool Calling：

```text
LLM.bind_tools
-> 同轮并行执行彼此独立的 knowledge_retrieval / web_search / document_read
-> 等待本轮全部 ToolMessage
-> 有依赖的工具进入下一轮，MCP 和 document dry-run 单独串行调用
-> knowledge_document_create/update/delete dry-run
-> TaskPlan confirm
```

启动：

```powershell
.\.venv\Scripts\uvicorn.exe fast_app.main:app --reload
```

如果服务启动时仍是：

```env
AGENT_DOCUMENT_TOOLS_ENABLED=false
```

或：

```env
AGENT_DOCUMENT_TOOLS_DRY_RUN_ONLY=true
```

完整流程会失败。这是正确行为，因为服务端没有开放真实工具执行。

### 2.1 Agent 多步骤 TaskPlan 人工验收

当前 15-7 已经具备最小版 LLM 多步骤任务计划闭环。验收这个链路时，推荐使用 `tool_manager`，并使用下面这种表达，避免 Prompt Guard hybrid 模式把“查询知识库并保存”误判成 Prompt Injection：

```text
请根据混合检索相关资料整理一份报告，文件位置 development/manual-taskplan-test.md
```

预期链路：

```text
/auth/login
-> /rag/chat
-> 生成 agent_task_plan_id
-> LLM 原生 knowledge_retrieval ToolCall completed
-> ToolMessage 返回资料或候选文档
-> LLM 原生 knowledge_document_create ToolCall completed
-> knowledge_document_create waiting_confirmation
-> 等待 POST /agent/task-plans/{task_plan_id}/confirm
```

验收重点：

```text
1. /rag/chat 返回 agent_task_plan_id。
2. agent_task_status=waiting_confirmation。
3. task_confirmation_required=true。
4. task_confirm_endpoint=/agent/task-plans/{task_plan_id}/confirm。
5. runtime/agent-task-plans/ 下生成 TaskPlan JSON。
6. 确认前 docs/knowledge-base-acl-test/development/manual-taskplan-test.md 不存在。
```

### 3. 旧单工具自动流程已移除

旧的自然语言 create/update/delete 单工具验收脚本和 CLI 参数已经删除。当前代码已经删除 `AgentDocumentActionPlanner` 入口，RAG Agent 不再把普通自然语言文档动作直接转换成单工具执行链路。

不要再把下面这类输入作为 15-7 主验收项：

```text
请创建 development/x.md，内容是……
请更新 development/x.md，内容是……
请删除 development/x.md
```

这类输入应回到普通 RAG / direct answer，或因为不属于白名单 TaskPlan 而不产生 `agent_task_plan_id`。

### 4. 非流式接口：手工测试 TaskPlan 确认

如果你想自己观察 TaskPlan 生成后的人工确认环节，使用 `--manual-confirm-task-plans`。

这个参数的含义是：

```text
1. CLI 调用 /rag/chat。
2. 如果响应里有 agent_task_plan_id 且 task_confirmation_required=true，说明文档创建步骤等待人工确认。
3. 人工检查 runtime/agent-task-plans/ 下对应 TaskPlan JSON。
4. 输入 true 后调用 POST /agent/task-plans/{task_plan_id}/confirm。
5. 未确认时 TaskPlan 保持 waiting_confirmation，源文件不会写入。
```

注意：CLI 的 `true` 只是本地人机确认按钮；后端仍会重新做权限裁决。

manager 用户是最适合手工测试 TaskPlan 报告生成和保存的账号：

```powershell
.\.venv\Scripts\python.exe scripts\phase_15\test_rag_agent_login_multiturn_cli.py `
  --base-url "http://127.0.0.1:8000" `
  --username "tool_manager" `
  --password "Manager123456!" `
  --mode hybrid `
  --top-k 5 `
  --candidate-k 10 `
  --manual-confirm-task-plans
```

启动后输入：

```text
请根据混合检索相关资料整理一份报告，文件位置 development/manual-cli-test.md
```

预期：

```text
1. CLI 打印 answer。
2. answer 中能看到 agent_task_plan_id 和 confirm_endpoint。
3. CLI 打印 detected_agent_task_plan_id=...
4. CLI 提示 confirm true?>。
5. 输入 true 后，CLI 调用 TaskPlan confirm 接口。
6. 返回 manual_confirm=passed，且 executed=true / status=completed。
7. 本地生成 docs/knowledge-base-acl-test/development/manual-cli-test.md。
```

如果用 reader 登录：

### 5. 结构化流式接口测试

结构化流式接口使用 `/rag/chat/stream/events`。它是 React 前端主线，不是 legacy token-only stream。

启动命令：

```powershell
.\.venv\Scripts\python.exe scripts\phase_15\test_rag_agent_login_multiturn_cli.py `
  --base-url "http://127.0.0.1:8000" `
  --username "tool_manager" `
  --password "Manager123456!" `
  --stream-events `
  --show-stream-events `
  --manual-confirm-task-plans
```

先输入普通 RAG 问题：

```text
RAG 后端部署步骤是什么？
```

预期结构化流式接口会打印：

```text
[event=sources]
source_count=...

[event=answer_delta] 或 guard_sanitized / guard_blocked
...

[event=done]
stream_done=passed
```

再输入 TaskPlan 请求：

```text
请根据 RAG 权限测试相关资料整理一份报告，文件位置 development/manual-stream-test.md
```

预期：

```text
[event=agent_task_plan_created]
能看到 task_plan_id、task_kind、status、target_path。

[event=agent_task_waiting_confirmation]
能看到 confirm_endpoint=/agent/task-plans/{task_plan_id}/confirm。

如果启用了 --manual-confirm-task-plans，CLI 会提示 confirm true?>。
输入 true 后调用 TaskPlan confirm 接口并执行。
```

结构化流式测试重点不是看最终回答质量，而是确认：

```text
1. /rag/chat/stream/events 能输出 agent_task_plan_created。
2. 能输出 agent_task_waiting_confirmation。
3. 普通 sources / answer_delta / done 事件仍正常。
4. 文档写入仍然必须经过 TaskPlan confirm 接口。
```

legacy `/rag/chat/stream` 仍是 token-only 兼容接口。这个 CLI 不把新的 TaskPlan confirm 测试放到 legacy stream 上；15-7 的前端主线应使用 `/rag/chat/stream/events`。
