## 二、改造背景与内容（面试 30 秒版）

**问题**：`uvicorn --workers 4` 或多容器部署时，进程内 `asyncio.Lock` 失效，同一个 `task_plan_id` 可能被两个 Worker 同时执行——LLM 费用翻倍、草稿互相覆盖、取消状态被旧进程覆盖为"完成"。

**方案**：把"锁"从进程内存搬到数据库行，并给每次持锁发放"代际编号"：
- 4 张 PostgreSQL 事实表（TaskPlan 快照 + Runtime 登记 + 幂等命令 + 容量槽）；
- 数据库租约（条件 UPDATE 领取、心跳续租、到期自动释放）+ **fencing token**（旧持有者恢复后所有写 SQL 因代际不符必然失败）；
- `record_version` 原子 CAS（`UPDATE ... WHERE record_version=:expected`，0 行即冲突，杜绝丢失更新）；
- 状态机单调转换（`cancelled` 为受保护终态）；
- `Idempotency-Key` + 命令表（同键重放结果，失败/被拒后同键可复活重试，崩溃孤儿定时收敛）；
- 全局容量槽（`FOR UPDATE SKIP LOCKED`，超限 429 + Retry-After）。

**规模**：修改 20 个文件、新增 14 个文件（含 11 个代码/脚本文件，覆盖 Repository / Store / Runtime / LeaseManager / Executor / 路由 / 依赖 / Alembic 0013 迁移 / 5 个测试与运维脚本）。

## 六、面试问答素材（高频问题预答）

**Q1：为什么"进程内锁 + 乐观版本号"不够？**
asyncio.Lock 只在一个进程内互斥；`--workers 4` 是 4 个进程。旧实现的 `record_version` 是"读→比较→写"三步，两个进程同时通过检查后互相覆盖（实测复现：两个旧写入者都以 expected_version=1 成功返回 2）。必须把"比较+写入"合并为一条 `UPDATE ... WHERE record_version=:expected`，用受影响行数判断成败。

**Q2：有租约为什么还要 fencing token？**
租约防"别人抢"，防不住"自己复活"：Worker A 拿到租约后暂停（GC/休眠），租约过期、B 接手，A 恢复后仍握有旧内存继续写。fencing token 每次领取 +1，A 的所有写 SQL 带 `WHERE lease_fence_token=旧值` → 全部 0 行失败。类比：门禁卡代际注销。

**Q3：20 个并发请求为什么是"19+1"而不是"19 排队"？**
双层防护：进程内 fail-fast 锁先拦（本进程内重复秒回 409、零 DB 开销，实测 17/20 在这里被拦）；跨 Worker 的漏网请求由数据库租约条件 UPDATE 拦截（0 行即 409）。第一层是性能优化，第二层才是正确性权威。

**Q4：幂等键最容易被忽略的坑是什么？**
终态死锁：很多实现只处理"succeeded 重放"和"running 繁忙"，忘了 rejected/failed 之后同键重试怎么办——我的原方案就踩了这个坑：容量 429 或瞬时失败后，按前端语义复用同一 key 重试会永远 409。修复：rejected/failed/孤儿 running 都允许"复活重试"，只有 succeeded 重放。另外崩溃遗留的 running 命令要有定时收敛（孤儿回收）。

**Q5：cancel 竞态怎么解决？**
cancel 在单事务里 `SELECT FOR UPDATE` 锁行 → 写 cancelled → 版本+1、代际+1、清租约。运行中的旧执行者随后保存终态时，条件 UPDATE 必然 0 行；再配合"冲突后重读权威状态，确认已 cancelled 则静默收敛"，既保证取消不可被覆盖，又不会把成功的取消误报为执行失败。

**Q6：这套改造的性能代价？**
控制面读取（GET 任务详情）实测 26.9ms；写路径每次进度保存是一次条件 UPDATE（毫秒级）+ 可选导出。代价主要在"每个模型/工具边界多一次状态重读"，换来的是旧执行者失权后必然失败的安全保证。

**Q7：如何处理 LLM 方案的缺陷？（可讲审阅方法论）**
对生成式方案做了"方案声明 vs 真实代码"逐项交叉核验，抓出 5 个上线即失败缺陷——最典型的是状态机缺边：方案声称 `waiting_confirmation` 只能转 running/cancelled，但真实代码 confirm 在真实写入完成后**直接从 waiting_confirmation 保存 completed**，按原表实施终态保存必然 CAS 失败、任务永久卡死。教训：状态机必须对照真实代码的每个保存点核对。

**Q8：剩余风险如何管理？**
承认数据库层管不到已发出的网络请求（租约≠恰好一次）：真实写副作用靠下游业务幂等键（GitLab `(task_plan_id, source_id)` 唯一约束）兜底；checkpoint 双写小窗口、cancel 收敛延迟用监控（LEASE_LOST 计数、lease_until 余量）观测。
