## 一、结论

正式 P2 已按“10 个普通 RAG SSE + 3 个 Research confirm + 2 个 Document SSE”启动，并实测达到 `global_peak_active_requests=15`。但最终结论是 **不通过**：

1. 10 个普通 RAG 结构化 SSE 为 10/10 成功，且日志均为独立 `session_id`、`history_empty`。
2. Research 全局容量 2 生效，3 个 confirm 中 2 个进入业务路径、1 个稳定返回预期的 `429 AGENT_CAPACITY_EXCEEDED`；但两个执行者都因证据约束不足最终进入 `failed`。
3. 两个 Document SSE 都在 Supervisor 后第一次保存快照时触发 `AGENT_TASK_PLAN_VERSION_CONFLICT`，没有进入 Deep Document 工作流，也没有真正形成 Document 容量碰撞。

5. 测试结束后 TaskPlan 租约、Research/Document 容量槽均为 0，没有发现重复执行者或遗留占用。

因此可准确表述为：

> 该轮已经证明四 Worker 下可承接 15 个同时在途的混合请求，RAG SSE 和 Research 容量控制有效；当轮的 Document 状态机缺陷现已通过完整生命周期改造修复，但在 10+3+2 整轮复测前，Research 业务质量和 120 秒 P95 仍未达标，不能声称通过“10–15 人使用场景”验收。

### 4.3 Windows Worker 启动异常

第一次四 Worker 启动时，一个子进程出现 `WinError 10022` 并被 Uvicorn 替换。随后第一次 20 请求验收中，应用日志只看到 16 个请求，另外 4 个没有应用层记录，客户端最终在 180 秒超时。该轮被废弃，不能作为一致性通过证据。

停止整个测试进程树并干净重启后，四个 Worker 均一次启动完成，同一测试 20/20 收敛并通过。因此当前证据表明：

- TaskPlan 互斥本身通过；
- Windows 多 Worker 带病启动可能造成连接悬挂，是独立的部署可靠性风险；
- 生产部署不能只看 `/health`，还应验证期望 Worker 数并监控子进程重启。

## 五、Research 夹具停止闸门

第一个 Research 员工通过 `/rag/chat/stream/events` 创建 TaskPlan 时，外部 chat completion 的状态序列为：3 次 200，随后 2 次 400。日志明确记录：

```text
structured_output transport=json_schema attempt=1 error_type=BadRequestError
structured_output transport=json_schema attempt=2 error_type=BadRequestError
```

数据库中没有生成该请求对应的 TaskPlan，也没有得到 `waiting_confirmation`。

真实代码中的控制流是：`invoke_structured_model()` 只有在 `_transport_unsupported()` 命中特定错误文本时才切换 transport；本次 400 没有命中该分类，第二次同 transport 失败后直接 `raise`，所以没有尝试 `function_calling`、`json_mode` 或 `strict_json`。从调用顺序和已完成的 Planner 请求看，失败边界位于 Reviewer 阶段。

这是 P2 的硬阻断：三个 Research confirm 必须分别引用三个真实、归属于对应用户的 `waiting_confirmation` TaskPlan，不能伪造 ID 或用数据库手工快照冒充真实 Planner 结果。

### 5.1 修复后补充验证

2026-08-15 已修复上述 transport 分类缺陷。适配器现在读取 OpenAI-compatible SDK 的结构化 `status_code`；前三种协议遇到确定性 HTTP 400 时立即切换下一协议，不再原样重试同一个 400。Timeout、5xx 和 Schema `ValidationError` 的原重试边界保持不变。

使用同一员工、同一真实 `/rag/chat/stream/events` Research 请求复测，Reviewer 的实际降级序列为：

```text
json_schema       → 400 invalid_parameter_error
function_calling  → 400 invalid_parameter_error
json_mode         → 400 invalid_parameter_error
strict_json       → 200
```

复测耗时 78,655.285 ms，SSE 事件为：

```text
agent_route_selected
→ agent_task_plan_created
→ sources
→ answer_delta
→ done
```

最终创建 1 个 `waiting_confirmation` Research TaskPlan，`error` 为 0、`done` 为 1。该验证 TaskPlan 和对应 JSON/Markdown 导出物已经清理，没有用于后续 P2。因此原压测的“P2 未执行”结论不变，但 Reviewer transport 阻断已解除。

### 6.4 Document SSE 缺陷

| 场景 | HTTP | SSE 终态 | 耗时 | 数据库终态 |
|---|---:|---|---:|---|
| `document_accepted` | 200 | `AGENT_TASK_PLAN_VERSION_CONFLICT` | 25,849.161 ms | `created`, version 1 |
| `document_capacity_collision` | 200 | `AGENT_TASK_PLAN_VERSION_CONFLICT` | 20,302.025 ms | `created`, version 1 |

两个不同 `task_plan_id` 顺序复现同一个错误，根因已定位为生产代码中的状态转换缺陷：

1. `DocumentTaskExecutor.execute()` 完成 Supervisor 决策后，把 `document_workflow` 写入内存快照；
2. 此时 `plan.status` 仍是 `created`，代码先调用 `AgentTaskPlanStore.save()`；
3. `AgentTaskPlanRepository.save_snapshot()` 会按目标状态校验允许的源状态；
4. 状态机中 `CREATED` 的允许源集合为空，故 `created → created` 更新必然不命中 SQL 条件，并抛出 `AGENT_TASK_PLAN_VERSION_CONFLICT`；
5. 后面的 `RUNNING` 保存和 Deep Document 工作流从未执行。

租约配置为 90 秒、心跳 20 秒，两个错误在 20.302–25.849 秒内发生，所以不是租约过期。由于第一个 Document 在第二个真正领取容量前已经失败并释放槽，预期的“Document 容量 1 + 另一个 429”没有形成，Document 容量场景仍未得到验收。

数据库确认两个 Document TaskPlan 都没有 RuntimeRecord、没有 GitLab ChangeRequest；没有执行 confirm，也没有创建目标文件或触发 ES/Milvus 发布链路。
