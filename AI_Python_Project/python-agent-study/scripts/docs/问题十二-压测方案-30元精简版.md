# 问题十二：30 元预算精简版压测方案（审查修订版）

> 文档状态：压测执行设计，尚未正式开跑。
>
> 本版以当前真实代码为准，修正了旧版把普通 `POST /rag/chat` 当作唯一 RAG 负载入口、把 Document `confirm` 当作多 Agent 执行、容量槽配置矛盾、预期 429 计数错误以及“预算硬顶”没有脚本实现等问题。
>
> 结构化流式主线必须是：
>
> ```text
> POST /rag/chat/stream/events
> → pipeline.stream_events()
> → sources / answer_delta / guard_sanitized / guard_blocked /
>   Agent TaskPlan 事件 / done / error

>
> `POST /rag/chat` 仅用于开发调试，不在本次压测范围；不得使用 deprecated 的 `POST /rag/chat/stream` 作为新压测主线。所有 RAG 压测请求必须使用 `/rag/chat/stream/events`。

## 一、目标与结论边界

30 元预算只能完成“低预算负载验证”，不能完成正式容量认证。

本次必须验证：

1. 15 个真实独立员工按“10 个普通 RAG + 3 个 Research + 2 个 Document”同时参与混合业务负载。
2. 混合负载的全局在途请求峰值必须实际达到 15；不能用配置数量或重复身份代替实测峰值。
3. Research/Document 的数据库容量槽能够在多 Worker 下阻止超发。
4. 同 TaskPlan 争抢、幂等重放、取消和详情读取在负载下不破坏数据库事实。
5. 采集各模型真实 token 与费用，为后续更长时间的容量与稳定性验收估算预算。

最终报告只能使用以下口径：

- “15 个独立认证身份参与了 10+3+2 低预算混合业务负载，全局在途请求峰值实测为 15”；
- “本次样本中未知 5xx 为 0、SSE 协议错误为 0”；
- “容量超限请求按当前 API 契约被准确拒绝，未发现槽位超发”；
- “已获得当前模型矩阵下的单请求 token、费用和延迟样本”。

禁止写：

- “系统支持 15 人并发”；
- “通过正式容量验收”；
- “P95 达到生产 SLO”；
- “30 元内可以覆盖未来完整压测”。

本方案按用户要求不执行“15 个纯结构化 SSE 请求”单独轮次。15 并发只通过后文的 10+3+2 混合业务场景验证；P0 的 3 次/7 次单身份串行请求仍保留为费用和协议校准，不属于被略过的并发轮次。

## 二、必须遵守的当前工程事实

### 2.1 RAG 接口边界

| 用途 | 接口 | 本次用途 |
|---|---|---|
| React/新功能结构化流式主线 | `POST /rag/chat/stream/events` | 普通 RAG 背景负载、Document 多 Agent 创建、SSE 协议验收 |
| 开发调试接口 | `POST /rag/chat` | 不压测；不计入任何请求数、延迟、成功率或费用样本 |
| deprecated token-only 兼容链路 | `POST /rag/chat/stream` | 不测试，不增加新能力 |

结构化 SSE 客户端必须完整读取响应体直到 `done` 或 `error`，不能只判断 HTTP 200 后立即断开。每次请求至少记录：

- HTTP 状态和 `Content-Type`；
- 首个 SSE 事件耗时；
- 首个 `answer_delta` / `guard_sanitized` / `guard_blocked` 耗时；
- 完整流耗时；
- 事件名称序列和事件数量；
- `sources` 数量；
- `task_plan_id`（如果产生 Agent TaskPlan）；
- 唯一终态 `done` 或 `error`；
- `error.data.code`（如果失败）。

普通安全 RAG 请求的成功条件：

1. HTTP 200 且 `Content-Type` 为 `text/event-stream`；
2. 所有 `data` JSON 均可解析；
3. `sources` 出现在回答事件之前；
4. 至少出现一个 `answer_delta` 或 `guard_sanitized`；
5. 恰好一个 `done`，且没有 `error`；
6. 客户端确实读到 EOF，不能把半途断流记为成功。

专门的 Prompt Guard 样本可以出现 `guard_blocked`，但必须放入命名 `sse_scenarios` 并显式设置 `"allow_guard_blocked": true`；普通 RAG 出现未声明的 `guard_blocked` 按协议失败处理。

### 2.2 Research 与 Document 生命周期不同

Research 的昂贵业务执行发生在：

```text
先通过 /rag/chat/stream/events 创建 waiting_confirmation Research TaskPlan
→ POST /agent/task-plans/{id}/confirm
→ Research Worker 真正执行
```

Document 多 Agent 的昂贵内容生产发生在：

```text
POST /rag/chat/stream/events
→ Agent Router / Planner
→ AgentTaskExecutor.execute()
→ DocumentTaskExecutor.execute()
→ Deep Document Researcher / Writer / Reviewer
→ waiting_confirmation
```

Document 的 `POST /agent/task-plans/{id}/confirm` 只确认已经冻结的 dry-run 事实并执行 GitLab/ES/Milvus 等真实副作用，不会重新运行 Document 多 Agent。因此：

- 不能再用“一个 Document confirm ≈200k tokens”作为 Document 模型负载；
- Document 多 Agent 容量必须通过“全新 Document 创建请求”验证；
- Document confirm 只能作为独立的真实副作用与幂等验收，必须使用隔离测试项目和可清理路径。

## 三、当前压测脚本能力

`scripts/tests/document_security/accept_agent_task_plan_load.py` 已完成本轮改造，当前真实能力如下：

1. 所有 RAG 请求固定调用 `POST /rag/chat/stream/events`；脚本中已经不存在对 `/rag/chat` 或 deprecated `/rag/chat/stream` 的 HTTP 调用。
2. 完整消费并解析结构化 SSE，检查：
   - `Content-Type=text/event-stream`；
   - 每个 `data` 都是 JSON object；
   - 回答事件不能早于 `sources`；
   - `done/error` 终态唯一；
   - 成功流必须包含 `sources` 和回答事件；
   - 终态后不能继续发事件。
3. 记录完整流耗时、首事件、首回答、source 数量、回答事件数、事件名称、TaskPlan ID/状态和协议错误。
4. `--request-count` 提供固定次数模式；P0 使用该模式。
5. `--duration-seconds` 必须和 `--max-request-count` 一起使用，时间或请求数任一先达到就停止创建新请求。
6. `--user-limit` 可在保留 15 人配置的同时，只选前 N 个身份执行；P0 使用 1，P2 普通 RAG 子负载使用 10。
7. `--skip-rag` 可只运行 control，用于 P1 的零模型调用测试。
8. control 支持：
   - `confirm/retry/cancel/get`；
   - `attempts` 固定次数；
   - 指定 `idempotency_key`；
   - `replay=false` 关闭隐式重放；
   - `expected_error_codes` 声明预期拒绝。
9. `sse_scenarios` 支持命名的 Agent SSE 请求；Document 碰撞请求可使用 `wait_for_capacity_workload=document`，只读轮询 PostgreSQL，确认请求 A 已持有容量槽后才启动请求 B。
10. `--stop-rag-when-scenarios-complete` 会在所有 control 和命名 SSE 场景收敛后设置共享停止信号，使背景 RAG 不再为了填满固定时长继续花费 token。
11. 报告将 `success`、`expected_rejection`、`http_error`、`sse_error`、`protocol_error`、`network_error` 和 `unexpected_5xx` 分开统计；预期容量拒绝不进入业务成功率分母。
12. RAG、control 或命名 SSE 场景出现首个未知 5xx、SSE error 或协议错误时会设置共享停止信号，所有 RAG worker 停止派发新请求；已经在途的请求仍安全收尾。
13. 报告不保存 JWT、API Key、query 正文或模型 Prompt，只保存身份别名、事件摘要、TaskPlan ID 和指标。
14. 报告记录 `global_peak_active_requests`，其口径覆盖普通 RAG、Research control 和 Document SSE；混合并发 15 必须由该字段的实测值证明。

对应的确定性回归是：

```powershell
$env:PYTHONPATH="src;scripts\tests\document_security"
.\.venv\Scripts\python.exe -B `
  scripts\tests\document_security\test_agent_task_plan_load_driver.py
```

脚本不读取 DashScope 实时余额；费用停止线仍依赖 P0 后的人工控制台核对和 `--max-request-count` 请求数保险丝。Research TaskPlan ID、Document 请求内容、JWT 和隔离 GitLab 路径仍是执行前必须准备的场景数据，脚本不会伪造业务事实。

### 4.1 先填价格，不使用统一“元/M”估算

### 4.2 预算不是现成的实时硬顶

当前工程和压测脚本没有 DashScope 实时余额 API，因此本次采用“小批量 + 阶段闸门”：

1. P0-A 只跑 3 次结构化 SSE；
2. 人工核对 DashScope 分模型用量和账单；
3. 按实测最高单请求费用重算后续最坏成本；
4. 只有预计累计费用不超过 24 元，才允许进入下一阶段；
5. 24 元为停止线，保留 6 元处理在途请求和账单延迟；
6. 任一模型免费额度消耗达到本次允许额度的 80%，跳过所有可选阶段；
7. 达到 100% 或发现费用统计无法确认，立即停止派发新请求。

“停止”表示不再创建新请求；已经在运行的请求应优先取消或等待安全终态，不能直接杀进程制造孤儿 TaskPlan。

阶段费用计算：

```text
阶段费用 = Σ模型(
  输入 tokens × 输入单价
  + 输出 tokens × 输出单价
  - 可确认的免费额度抵扣
)
```

P0 校准完成前，不预先承诺 Research 150k、Document 200k 或 P2 总计 620k；这些都只能作为历史估算，不能作为执行事实。

选择 `6/4/2` 而不是旧版 `4/3/1` 的原因来自真实 pilot 与 2026-08-15 失败样本：

1. **子问题 6**：Planner 初稿为 3 个 SubQuestion，Reviewer 为修复来源覆盖关系增加了 1 个综合 SubQuestion，最终形成 4 个 SubQuestion、5 个 Requirement；旧上限 3 因而触发过 `PLAN_SUB_QUESTION_LIMIT_EXCEEDED`，4 是"刚好够"、零余量。正式题仍只有三项明确义务和一个综合步骤，预计实际产出 4~5 个；上限 6 给 Reviewer 再留 1~2 个拆解余量，不直接放宽到默认 8，控制 token 成本。
2. **每 Worker 工具调用 4（代码上限）**：历史部署文档 pilot 出现"两个 Worker 在最终答案前耗尽工具调用预算"；3 次只够一次初始检索、一次查询收敛和一次纠正检索，没有第四次补救机会。4 是代码允许的最大值。
3. **纠正轮 2（代码上限）**：confirm pilot 的 3/3 Requirement 均为 `REQUIREMENT_EVIDENCE_INSUFFICIENT`，说明 Evaluator 判证据不足后只有 1 次补救不足以收敛证据质量；2 次是代码允许的最大值。
4. **Worker 超时 150 秒**：上次 3 次工具调用 + 1 次纠正轮下 confirm 实测 `121986.085 ms` 已超过 120 秒总超时；增加工具调用与纠正轮后按 120 秒执行等于把失败点从"证据不足"换成"超时"。150 秒覆盖 4 次调用 + 2 次纠正轮的时间空间，但仍保留以下纪律：单请求 confirm pilot 必须提供分阶段耗时证据；若 pilot 显示 150 秒内仍有富余或不足，再据此复核，不得无证据继续放宽。

## 六、统计与验收规则

### 6.1 不得混用的统计口径

分别报告：

1. 普通 SSE RAG 成功率；
2. Research/Document 被受理任务成功率；
3. 预期容量拒绝命中率；
4. 预期 409 命中率；
5. 未知 4xx；
6. 5xx；
7. SSE `error`；
8. 网络/客户端超时；
9. Prompt Guard 预期阻断。

预期的 409、HTTP 429 和 SSE capacity `error` 不进入普通 RAG 成功率分母，但必须与场景期望数量严格一致。超出或少于期望都失败。

### 6.2 SSE 指标

- `time_to_first_event_ms`；
- `time_to_sources_ms`；
- `time_to_first_answer_event_ms`；
- `total_stream_ms`；
- `event_count`；
- `answer_event_count`；
- `source_count`；
- `terminal_event`；
- `stream_parse_error_count`；
- `client_disconnect_count`。

P50/P95 只作为本批样本描述。样本量不足时不用于生产 SLO 承诺。阈值应在 P0 校准后确定，不能预先用普通非流式请求的历史 P95 代替 SSE 阈值。

### 6.3 数据库一致性后验

压测结束后必须检查：

- 所有受理 TaskPlan 的状态和 `record_version`；
- command 状态、幂等键、完成时间和错误码；
- `lease_owner/lease_until` 已释放；
- capacity slot 没有残留租约；
- fencing token 单调；
- cancelled 没有回退；
- 没有同一 TaskPlan 的两个 succeeded 执行命令；
- Document 没有重复 MR、重复提交、重复发布版本；
- 没有新的长期 running 孤儿命令。

停止后先让已受理任务收敛或通过控制 API 取消，再停止服务。不要直接结束所有 Worker 后把遗留 running 记录当成正常结果。
