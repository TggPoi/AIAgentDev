# 问题十二：复杂任务约 320 秒延迟 —— 根因分析报告（LangSmith Trace + 测试报告文档 + git 恢复快照）

> 分析方法：① 从 LangSmith 拉取历史慢请求调用树（105/76/68 节点）；② 交叉核对 `GitLab文档变更端到端测试报告.md`（场景 3）与 `多Agent端到端测试复盘与工程规则.md`；③ 从 git 对象库恢复 320s 验收任务的 TaskPlan 快照。

## 一、结论摘要（先说答案）

1. **"320 秒"确有其事，且就是文档 Deep Agent 链路**：`GitLab文档变更端到端测试报告.md` §25 记录了 2026-07-27 场景 3 最终修复验收——全新 TaskPlan `task_plan_20260726175005_8acd72b40d07`，`POST /rag/chat/stream/events` 耗时约 **320.0 秒**，**成功**进入 `waiting_confirmation`（正文 3,738 字符、Reviewer approved 0.92、checkpoint released）。这是当前文档链路的**已知性能基线**；复盘文档 §5 明确要求"必须保留性能回归基线，不能视为最终企业级延迟目标"。
2. **320s 之前是 334.7s/302.4s 的失败（BUG-001）**：原 TaskPlan `task_plan_20260726124322_099b2df31bde`（07-26）首次 334.7s、恢复 302.4s，均撞 `AGENT_DOCUMENT_WORKER_TIMEOUT_SECONDS=300` 失败——**45 次模型调用未收敛**（44 次完成、累计 290s、中位数 2.5s、最长 51.4s、无 SDK 重试）。修复轮（git commit `74eba99`）落地了当前代码中的全部对应配置：Researcher 独立 120s 超时 + 12 次上限、外层 300→480s、Coordinator/Reviewer 流式化、确定性组装批准结果、36 次共享预算与 2 轮返工保险丝，**BUG-001/005 已关闭**。
3. **与 LangSmith 实测互证**：本报告用 LangSmith 拆解的 359.9s/267.9s/252.9s 是 **Research 确认链路**的另一组样本（三波串行、单次 LLM 答案 40–70s、一次 120s worker 超时）——两条链路共同瓶颈一致：**模型生成吞吐 + 串行阶段**，与文档链路 320s 相互印证。
4. 时间构成（合并两组证据）：
   ```
   总耗时 ≈ 串行阶段 × 每阶段最长模型调用
           + 单次 LLM 生成 40–70s（qwen3.7-plus，约 50–60 tokens/s）
           + （历史）300s 外层超时撞线 / （当前）120s Researcher 超时撞线
           + 收尾综合 37–62s + Prompt Guard 8–11s
   ```
5. **不是代码 bug**：无 SDK 重试风暴（trace 中每次调用只出现一次；文档链路当前 `max_retries=0`）、检索/rerank/checkpoint 写库都不在时间热点内（毫秒~2 秒级）。

## 五、根因分层（按占比）

| # | 根因 | 占比（估） | 性质 |
|---|---|---|---|
| R1 | **qwen3.7-plus 单次答案生成 40–70s**（输出 2k–3.8k tokens ≈ 50–60 tokens/s） | 75–85% | 模型侧吞吐，非工程缺陷 |
| R2 | **波次串行放大**：每波时长 = 波内最慢 worker；总长 ≈ Σ各波 | 结构性 | DAG 依赖决定，不可消除 |
| R3 | **120s worker 超时撞线**：sq-6 满额 120s 被取消 → 白等 + 子问题失败 | 仅 359.9s 样本有 | 配置偏紧 |
| R4 | final synthesis 单次 37–62s（最后一个串行段，无法并行） | ~15–20% | 模型侧 |
| R5 | Prompt Guard 输出分类 8–11s/次 | ~3–4% | 安全开销 |

**排除项**（都已核实）：SDK 自动重试（`AGENT_DOCUMENT_RESEARCHER_MAX_RETRIES=0`，trace 无重复调用）、检索/rerank（未进时间热点）、LangGraph checkpoint 写库、文件 IO。

## 六、优化建议（按风险从低到高）

**低风险，压测前可先做：**
1. **Worker 超时 120s → 180s**：避免"差一点完成却被取消"的 120s 白等与 WORKER_TIMEOUT 失败。Research 链路没有文档任务那种 480s 总预算约束，租约由心跳续租兜底；SSE 网关 read timeout 600s 也放得下。改动点：`.env` 的 `AGENT_RESEARCH_WORKER_TIMEOUT_SECONDS`。
2. **输出分类提速实验**：`PROMPT_GUARD_MODE=hybrid → rule` 对比最终答案链路，可省 8–11s/次（安全策略需先书面确认 rule-only 的拦截率可接受）。
3. **补分阶段耗时观测**：在 `agentic_research_executor` 增加 wave/attempt/answer/synthesis/guard 分阶段日志与"单次 LLM 调用 >30s"计数（指标化），后续调优不用再翻 trace。

**中风险（需模型实验对比）：**
4. **模型分层**：子问题答案与 final synthesis 用更快的 qwen3.6-plus 做 A/B 对比（质量 vs 延迟，建议用 rag-eval 框架跑 10–20 条回归题再决定）；若质量达标，350s → 200s 级别是可预期的。
5. **输出长度约束**：研究答案 3k tokens 是否必要，属业务质量决策，不改语义前不要动。

**不建议做：**
- 改波次串行结构（DAG 依赖是业务语义）；提高波内并行度（受模型 429 配额限制，压测中已见外部延迟是瓶颈）。

## 七、对压测方案的影响（重要，需同步修订）

1. **单复杂任务时长预估修正**：Research confirm 实测 **250–360s/任务**；**文档 Deep Agent 任务实测基线 ≈ 320s**（07-27 最终验收，成功路径）——两者同量级。容量槽 `research=2 / document=1` 下，批时长 ≈ 最长单任务 + 少量调度开销。
2. **压测报告新增采集项**：first_token 时间、单次 LLM 调用耗时分布、120s Researcher 超时计数（LangSmith 均可导出）——这些是"模型侧瓶颈"的直接证据，也是决定是否换模型的依据。
3. **压测前先做模型降配实验**（§六第 4 条），再确定压测绑定哪个模型，避免整份压测数据绑定慢模型。
4. **320s 作为性能回归基线写入压测方案**：复盘文档要求"保留性能回归基线"——P0 校准批复测一次完整场景 3 类文档任务并记录分阶段耗时；任何优化（超时/模型/Guard）都必须与 320s 基线对比，而不是只看"没超上限"。
