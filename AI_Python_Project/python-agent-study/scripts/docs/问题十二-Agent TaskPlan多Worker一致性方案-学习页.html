Chapter 1 · 先讲人话，再看代码

问题不是“多人用了系统”，而是“同一任务被多个执行者同时认领”

15 个员工各自查询不同问题，并不会天然产生 TaskPlan 状态冲突。真正危险的条件是：同一个 task_plan_id 的 confirm、retry、resume 或 execute 被重复提交，而且这些请求落到不同进程或不同实例。

输入

同一个 TaskPlan 的重复控制请求。来源可能是双击、客户端超时重试、负载均衡重试或两个管理员同时操作。

危险变化

两个 Worker 都以为自己是唯一执行者，同时调用模型、写 RuntimeRecord、生成草稿或触发真实副作用。

必须输出

只有一个执行者获得数据库权威执行权；其他请求要么重放结果，要么稳定返回 409/429，不能悄悄重复执行。

Chapter 2 · 从你学过的锁理论出发

并发基础：为什么一把正确的锁仍然可能保护错范围

2.1 进程、线程、协程：先分清“内存是否共享”

执行单位内存关系本工程对应关键风险
协程同一线程、同一进程内共享对象；在 await 处让出执行权。FastAPI 请求协程、心跳协程、SSE 轮询协程。读完状态后发生 await，回来时状态可能已经变了。
线程同一进程内共享堆内存，各线程有独立调用栈。asyncio.to_thread() 执行同步 checkpoint / 文件导出。共享对象需要线程安全；但线程锁仍不能保护另一个进程。
进程每个进程有独立地址空间，普通 Python 对象不共享。uvicorn --workers 4 的四个 Worker。四份 asyncio.Lock 互相看不见。
实例 / 容器不仅内存独立，甚至可能运行在不同机器。负载均衡后多个 FastAPI 实例。只有共享数据库、队列或协调服务能提供权威互斥。

最小实验：同一进程里的锁确实有效

教学示例 · asyncio_lock_same_process.py
import asyncio

lock = asyncio.Lock()

async def work(name: str) -> None:
    if lock.locked():
        print(name, "发现锁已占用")
    async with lock:
        print(name, "进入临界区")
        await asyncio.sleep(0.2)
        print(name, "离开临界区")

async def main() -> None:
    await asyncio.gather(work("A"), work("B"))

asyncio.run(main())

你会看到 A、B 不会同时进入临界区。这就是当前工程保留 _TaskPlanLockRegistry 的原因：同一 Worker 内可以极快地拒绝第二个请求，不必先访问数据库。

2.2 锁的关键不是“有没有”，而是“谁能看见它”

每个 Uvicorn Worker 导入模块时，都会各自执行一次 _TASK_PLAN_LOCKS = _TaskPlanLockRegistry()。四个 Worker 得到四个不同对象。因此 Worker 1 的字典里有 task_plan_123，Worker 2 的字典仍然是空的。

教学示例 · Windows 下两个进程各自拥有自己的锁
import asyncio
from multiprocessing import Process
import os

async def local_lock_demo() -> None:
    lock = asyncio.Lock()
    async with lock:
        print(f"pid={os.getpid()} acquired its own lock")
        await asyncio.sleep(0.5)

def worker() -> None:
    asyncio.run(local_lock_demo())

if __name__ == "__main__":
    p1 = Process(target=worker)
    p2 = Process(target=worker)
    p1.start()
    p2.start()
    p1.join()
    p2.join()
  1. 两个进程都创建了名为 lock 的对象，但它们位于两个地址空间。
  2. 两行输出都会显示 acquired，这不是锁失效，而是锁从来没有被共享。
  3. 要跨进程协调，判定依据必须落在双方都能看到的 PostgreSQL 行上。

2.3 原子性、TOCTOU 与丢失更新

TOCTOU 是“检查时”和“使用时”之间出现时间窗口。旧 Runtime 实现的逻辑是：先读取 version，再在 Python 中比较，最后普通写回。问题在于，两个 Writer 可以在检查阶段都看到 version=1。

非原子读改写

W1 读到 version=1。

W2 也读到 version=1。

W1 写 version=2。

W2 再写 version=2，覆盖 W1。

数据库原子 CAS

W1 执行 UPDATE ... WHERE version=1，更新 1 行。

数据库立即把 version 改为 2。

W2 的相同 UPDATE 更新 0 行。

W2 根据 rowcount=0 得知自己拿的是旧快照。

文件“原子替换”不是业务“原子状态转换” os.replace() 能保证读者不会看见半个 JSON 文件，但不能判断这个完整 JSON 是不是旧快照。旧执行者仍可能把完整的 completed 文件覆盖到刚保存的 cancelled 文件上。原子文件写解决的是“文件完整性”，CAS 解决的是“业务新旧顺序”。

为什么不能只换成“跨进程文件锁”

为什么"改账本"只能由金库管理员一个人做？因为改账本有个铁律：必须同时完成"看条件"和"写结果"。如果大堂经理、档案员都能自己改，就会出现第 2 章讲过的丢失更新——你看着旧账做决定，写下去时账已经变了。所以工程规定：谁都可以收申请单、谁都可以引导流程，但只要涉及"根据条件改数据"的 SQL，一律只能写在 Repository 这一个文件里。这就是图里 Repository 下面标的"唯一并发 SQL 边界"——"边界"的意思是：线外面的人不允许干这件事。

下面是这一章你会反复遇到的词，先集中解释一遍，后面每出现一次就不再重复：

术语人话解释生活类比
事务（transaction）一组动作"一口气办完"：要么全部成功，要么全部作废，不存在办一半转账：扣你的钱和加对方的钱必须同时成功，否则都不算数
租约（lease）一块"此任务归我办理"的牌子，带有效期，到期自动失效租房合同：租期内只有你能住，到期不续约自动作废
条件 UPDATE一条"改数据"的 SQL 带着条件——不满足条件就一行都改不动"如果价格还是 100 元就成交"——价格变了，这句话自动失效
fencing token（栅栏令牌）每次"换人办理"都会 +1 的编号，用来识别这是第几任办理人门禁卡代次：新卡发下来，旧卡刷卡就会被拒
SKIP LOCKED抢车位规则：别人正在锁的车位，我不等它，跳过它找下一个停车场找位：这个车位正在被占，直接开过去找下一个空位
幂等键（idempotency key）申请单编号：同一编号的事，系统保证只办一次挂号单号：拿同一个号去两次窗口，也不会给你办两次
Session和数据库的一次"通话"，办完就挂断打一次电话：说完就挂，不占线

4.3 金库管理员办一件事：一口气做三件事

所有控制操作（confirm 确认、retry 重试、cancel 取消）最后都会走进 Repository 的同一个方法：begin_operation()（repository L119）。它在一个事务里，一口气依次做三件事：

  1. 查申请单编号——这件事以前办过吗？（防"重复办理"）
  2. 领执行权——这个任务现在归我管吗？（防"两个人同时办"）
  3. 领车位——公司还有空车位给我吗？（防"同时办太多重活"）

"一口气"是关键：三件事在一个事务里，任何一件失败，前面做的全部作废——不存在"查完编号发现重复，但牌子已经挂上了"这种半吊子状态。

第一件事：查申请单编号（防止同一件事办两次）

要解决的问题：用户双击"确认"按钮、或者网络超时后客户端自动重试，同一件事会到达服务器两次。如果两次都照办，任务就被执行两遍。

解决思路：客户端每次发控制请求都要带一个"申请单编号"（幂等键，HTTP 头里的 Idempotency-Key）。数据库规定：同一个任务 + 同一种操作 + 同一个编号，只能存在一条记录。第一单进来时把记录存进去；第二单带着相同编号进来，数据库会拒绝存储（编号重复），于是代码知道"这单以前来过"，改去查老记录：

            pg_insert(AgentTaskPlanCommandTable)      # 往命令表插入
            .values(
                command_id=command_id,                # 这条记录自己的编号
                task_plan_id=task_plan_id,            # 是哪个任务的事
                operation=operation,                  # 办什么：confirm / retry / cancel
                idempotency_key=idempotency_key,      # ← 申请单编号（关键）
                request_hash=request_hash,            # 申请单内容的指纹（防同号不同内容）
                status="running",                     # 先记"正在办理"
            )
            .on_conflict_do_nothing(                  # ← 编号重复：什么都不做，存不进去
                constraint="uq_agent_task_plan_command_idempotency"
            )
            .returning(AgentTaskPlanCommandTable.command_id)  # 存成功就把记录编号返回
        )
    ).scalar_one_or_none()

两个词先解释掉：

  • 幂等：同一个操作做一次和做一百次，结果一样。给请求编上号，就是实现幂等的第一步——重试不再产生第二次业务；
  • on_conflict_do_nothing：人话就是"编号冲突就什么都不做"。数据库里有条硬规则（uq_agent_task_plan_command_idempotency，uq = 唯一约束），保证"同任务+同操作+同编号"只存得进一条。

然后代码看 inserted 的值分两种情况：

  • 存进去了（inserted 有值）：这单第一次来，继续往下办第二、第三件事；
  • 没存进去（inserted 是 None）：编号重复，这单以前来过。按老记录的状态分四路处理——以前成功了：直接把上次结果原样返回（重放）；以前还在办：看是不是已经没人管的"孤儿"（办的人早死了就允许重新办）；以前被拒/失败了：允许同一编号重试（复活）；编号相同但内容指纹不同：拒绝，防止拿旧编号干新事。这四路是第 7 章"幂等命令"的完整内容，现在知道"为什么查编号"就够了。

第二件事：领执行权（防止两个人同时办同一任务）

要解决的问题：就算申请单编号不重复，同一个任务还是可能被两个不同编号的请求抢——比如两个管理员同时点"确认"，或者第 2 章说的：同一个请求被网络分发到了两个不同的 Worker 进程。

解决思路：任务表上有一块"牌子"——租约，上面写着"这个任务现在归我（员工编号）办，有效期到 XX 时间"。要办任务，第一步就是挂这块牌子。

但挂牌子有个陷阱：不能"先看任务闲不闲、再挂"。因为"看"和"挂"之间哪怕只隔一瞬间，别人可能抢先挂了（第 2 章的 TOCTOU）。正确做法是把"看"和"挂"合成一个动作——把"任务必须空闲、状态必须允许"这些条件，直接写进"挂"这条 SQL 的条件里：

当前源码核心 · 第二件事：挂租约牌子（L221-249 节选）
task_row = (
    await session.execute(
        update(AgentTaskPlanTable)                    # 我要"改"任务表
        .where(                                        # ← 改之前先看条件，全满足才允许改：
            AgentTaskPlanTable.task_plan_id == task_plan_id,      # 改的是这个任务
            AgentTaskPlanTable.status.in_(allowed_statuses),      # 状态允许现在执行
            or_(                                     # 并且牌子是空的：
                AgentTaskPlanTable.lease_until.is_(None),          # 要么从没挂过牌
                AgentTaskPlanTable.lease_until <= func.now(),     # 要么旧牌已过期
            ),
        )
        .values(                                       # 条件全满足，就把牌子挂上：
            lease_owner=worker_id,                     # 牌子写"归我办"（我是几号员工）
            lease_until=_deadline(lease_seconds),      # 牌子有效期到什么时候
            lease_fence_token=AgentTaskPlanTable.lease_fence_token + 1,  # 第几任办理人：+1
            active_operation=operation,                # 正在办什么
        )
        .returning(                                    # 挂成功后，把两个数字读回来
            AgentTaskPlanTable.lease_fence_token,      # 我这一任的编号
            AgentTaskPlanTable.record_version,         # 任务的版本号
        )
    )
).one_or_none()

这行代码的威力在 .where(...) 里的条件：

  • 两个请求（哪怕在两个不同 Worker 进程里）同时执行这条 SQL，数据库会只让其中一个改成功——第一个把牌子挂上后，第二个再看"牌子是空的"这个条件就不成立了，它一行都改不动（返回空，即 one_or_none() 得到 None）；
  • 改不动的那方立刻明白"有人正在办"，向客户端返回 AGENT_TASK_PLAN_BUSY（HTTP 409，意思是"任务忙"）；
  • 上一轮压测的实测结果"4 个 Worker、20 个 confirm 抢同一个任务 → 19 个 409 + 1 个唯一执行者"，就是这行代码的功劳；
  • fencing token（+1）：每次成功挂牌，这个数字加 1，等于"第几任办理人"的编号。旧一任办理人手里还拿着旧编号，它之后想写任何数据都必须报编号，编号对不上就作废——这就是"旧人闭嘴"的实现。第 7 章专门讲。

第三件事：领车位（防止同时办太多重活）

要解决的问题：Research、Document 这类任务很贵（要调很多次大模型、跑几分钟）。公司规定：Research 最多同时办 2 件，Document 最多同时办 1 件。超过了就拒绝，而不是硬扛。

解决思路：有一张"车位表"（容量槽表）。Research 有 2 个车位，Document 有 1 个。牌子挂好了，还要领到一个空车位才能真正开工。车位被占也挂"已占用"的牌子、带有效期——和任务租约同一套思路。

当前源码核心 · 第三件事：领车位（L259-272 节选）
slot = await session.scalar(
    select(AgentTaskCapacitySlotTable)               # 在"车位表"里找车位
    .where(
        AgentTaskCapacitySlotTable.workload_type == workload_type,  # 车型要对：Research 还是 Document
        AgentTaskCapacitySlotTable.slot_no <= capacity_limit,      # 只找限定的车位号（如 1 号、2 号）
        or_(                                     # 车位要空着：
            AgentTaskCapacitySlotTable.lease_until.is_(None),        # 要么从没被占
            AgentTaskCapacitySlotTable.lease_until <= func.now(),   # 要么占用已过期
        ),
    )
    .order_by(AgentTaskCapacitySlotTable.slot_no)    # 从 1 号车位开始找
    .with_for_update(skip_locked=True)               # ← 关键：别人正在抢的车位，我跳过
    .limit(1)                                        # 找到一个就够
)

这里最值得学的是 skip_locked=True，人话解释：

  • 多个请求同时来抢仅有的 2 个车位时，先到的会把车位"锁住"；
  • 后来的请求看到车位被锁，不等它解锁，直接跳过它去找下一个空车位——这就是"跳过已锁行"；
  • 好处：不排队、不死锁（死锁 = 两个事务互相等对方解锁，谁都动不了）；
  • 一个空车位都没有（slot 为 None）时，代码走拒绝分支：把刚挂的任务牌子摘掉（归还未生效的租约）、在命令表记"被拒、原因=容量已满"，最后向客户端抛 429 AGENT_CAPACITY_EXCEEDED（"满了，请等会儿再试"）。

上一轮压测的"3 个 Research confirm 同时打进来 → 2 个受理 + 1 个 429"，就是第三件事的现场。

4.4 为什么每次办事都要自己拨电话、说完就挂（短 Session）

Repository 每个方法的开头都是同一句：async with self._session_factory() as session, session.begin():。这里的 session 就是"和数据库的一次通话"。工程规定：每个方法自己拨一次电话，办完立刻挂断，绝不两个协程共用一根线。

为什么？回到第 2 章学过的协程模型：一个 Worker 里有很多协程在同一个事件循环里轮流执行，其中包括一个特殊的后台协程——心跳：执行中的任务每 20 秒向数据库报一次"我还活着，租约续一下"。如果心跳协程和主执行协程共用同一个 Session：

  • 一根电话线不能两个人同时讲：SQLAlchemy 的 AsyncSession 不保证多个协程交替使用时的安全，事务会互相污染——你的事办到一半，别人的话插进来；
  • 占线太久别人打不进来：事务拖得越久，数据库连接和行锁被占得越久，所有其他请求都要等；
  • 挂断 = 结账：session.begin() 这段结束，要么提交（事情成真）、要么回滚（全部作废），不存在"办到一半的电话线"悬在那。

所以"短 Session"不是细节，它是"唯一 SQL 边界"能安全工作的配套纪律——每一笔裁决都是独立、短促、有明确结局的。

4.5 这一章背什么

合上页面，你应该能用自己的话说出三句话：

  • 全公司只有金库管理员能改账本——Executor 只引导流程，Store 只归档，能写"根据条件改数据"的 SQL 的只有 Repository 一个文件；
  • 办一件事 = 一口气三件事——查申请单编号（防重复）、挂牌子（防两人同办）、领车位（防超载），三件事在一个事务里，要么全成要么全废；
  • "先看后写"会被插队，所以工程把检查条件写进写操作本身（条件 UPDATE、SKIP LOCKED）——检查和写入一步完成，这是对第 2 章 TOCTOU 和丢失更新的工程级回答。

5.1 看图前先认三个缩写：PK / FK / UK

"四张表的身份关系"图里，字段名后跟着 PK、FK、UK 等缩写，含义如下：

  • PK = 主键（Primary Key）：唯一标识表中一行，非空且全表唯一。主表用 task_plan_id 作主键；
  • FK = 外键（Foreign Key）：本表某列引用另一张表的主键。数据库强制引用完整性：插入或更新时，外键值必须在被引用表中存在，否则报错，从而杜绝指向不存在行的记录；
  • UK = 唯一约束（Unique Constraint）：约束一列或一组列的值不允许重复（允许 NULL）；
  • 级联删除（ON DELETE CASCADE）：外键的可选行为——被引用的主表行被删除时，引用它的子表行一并删除，保证不残留悬空外键。

"为什么不能塞进主表"这三格，展开成具体理由：

  • Runtime 记录独立：只有 Document 任务使用它；它的 record_version 只跟随 Deep Agent 恢复登记的更新节奏增长，与主表快照版本是两条独立的增长线。塞进主表会让所有 Research 任务携带大量无意义的空字段；
  • 命令独立：一个任务一生会收到多条控制命令（confirm、cancel、retry……），每条命令有自己的结果与错误码，需要按行独立保存。塞进主表就只剩"最后一次操作"，无法回答"这个幂等键以前办过吗"，幂等机制失效；
  • 容量槽独立：槽是集群级共享资源，任务进入终态必须归还，槽上只记"当前占用者"。塞进主表等于把共享资源变成任务私有属性，其他任务无法查询全局剩余名额。

5.5 Deep Document 恢复登记表：Checkpoint 恢复前的安全门

先划清边界：agent_task_plan_runtime_records 不是 LangGraph checkpoint 本体，两者是两套独立数据。

LangGraph Checkpoint 本体Runtime 登记表

这层分工写在模型的 docstring 里（deep_document_runtime.py L174-176）："这不是 LangGraph State 的副本，而是业务层在恢复前用来做安全判断的最小事实集。record_version 保护的是这条 Store 记录，不是 LangGraph 内部的 checkpoint version。"

记录里存什么

登记表快照的字段定义在 deep_document_runtime.py L171-208，每项都是恢复判断要用的最小事实：

  • thread_id——LangGraph checkpoint 的稳定 thread，由服务端按 f"document:{task_plan_id}" 生成，不信任请求传入（L368-375，注释明确：否则用户可能读取或覆盖其他任务的 checkpoint）；
  • acl_fingerprint——执行时用户 ACL 的规范化指纹（SHA-256，L227-253），恢复前比对权限是否变化；
  • read_snapshots——已读文档的 doc_id / 路径 / SHA-256，不含正文（正文只进加密 checkpoint）；
  • candidates / used_tools——受控检索登记的候选事实摘要与已完成工具清单；
  • resume_count / status / expires_at——恢复累计次数、运行状态（running/failed/cleanup_pending）、保留截止时间。

阶段 3 · 崩溃：没有代码运行，现场原样保留

Worker 崩溃时没有任何代码执行清理，结果就是：LangGraph checkpoint（执行现场）和 Runtime 记录（安全判断事实）原样留在 PostgreSQL，记录状态仍是 running。这是设计目标而非疏漏——崩溃不破坏现场，恢复才有依据。需要区分的是：崩溃时没人改状态；而执行失败（模型报错、评审不通过）会主动把状态改成 failed 保留现场（L1581 _mark_checkpoint_resumable()），供 retry 找到它。

阶段 4 · retry：三道校验全过才恢复

用户点击 retry 后，恢复逻辑（deep_document_agent.py L1452-1502）不会直接进 checkpoint 执行，而是先做三道校验：

校验比对什么失败结果
① ACL 指纹当前用户权限 vs 上次执行时的权限不读旧 candidates/正文，删旧 thread，按当前权限重新检索

三道全过，代码才把记录改回 running、resume_count + 1（L1502-1509），然后从 checkpoint 继续执行。第②道校验单独存在的理由：ACL 没变不代表文档没变——任务中断期间若文档被修改，旧 checkpoint 的推理基于旧内容，恢复后的结论不可信，必须废弃旧现场重新执行。

阶段 5 · 完成：先删 checkpoint，再删记录

任务终态时调用 release()（deep_document_runtime.py L490-502）：先删 LangGraph thread，再删业务记录。顺序不可反——业务记录是管理入口，先删它就会留下无人管理的加密工作区。若删 checkpoint 失败，记录保留并标 cleanup_pending（L1618-1624），由维护命令下次重试，不假装已清理干净。

五个阶段连起来读：创建和更新都要过父租约这道门；崩溃不清理现场；恢复前过三道校验；终态先删 checkpoint 再删记录，删不掉挂"清理待办"。

补充：一次任务几十次 save 都写快照，checkpoint 还有用吗？

有用，两者不在同一个层次。区分清楚"三个写入动作"是理解这套机制的关键：

写入动作谁写写到哪里内容写入方式
save()（几十次）执行器显式调用agent_task_plans 表那一行业务事实：status、进度摘要、子问题结果、错误覆盖式，只保留最新一版
update_record()执行器显式调用agent_task_plan_runtime_records 表恢复资格事实：ACL 指纹、源文件 SHA、thread_id 指针覆盖式，带独立 CAS
checkpoint 写入LangGraph 每个节点完成后自动写PostgresSaver 的 checkpoint 表（加密）图内部执行现场：State、消息历史、虚拟文件、pending writes追加式，历史全保留

关键差别：快照里根本没有图内部的 State、虚拟文件、消息历史——这些只存在于 checkpoint。没有 checkpoint，崩溃后只能从头重跑整个图（所有 Researcher/Writer/Reviewer 的模型调用重新烧一遍）；有 checkpoint，LangGraph 从崩溃前最后一个节点继续执行，已完成的节点不重跑。

两条链路的持久化结构不同：

  • Research = 快照单轨：恢复粒度是子问题——每个子问题完成就 save 一次，子问题结果、证据、工具调用轨迹都落在快照的 worker_checkpoints 里；retry 时已完成子问题直接复用，只重跑未完成的。子问题之间没有需要保留的图中间状态，所以不需要 PostgresSaver；
  • Deep Document = 快照 + RuntimeRecord + checkpoint 三轨：图内部有几十个节点，节点之间有大量只在内存和虚拟文件里的中间状态，业务检查点密度不够恢复用，所以需要 LangGraph 原生 checkpoint 做节点级续跑，同时需要 RuntimeRecord 做更严的恢复资格校验。

三者的分工一句话：快照管"任务走到哪一步"，RuntimeRecord 管"有没有资格恢复"，checkpoint 管"从哪个节点继续跑"。

补充：TaskPlan 快照的四个作用

  • 控制面事实：状态机的每次跳转必须落库——save_snapshot 是主表唯一写入入口，状态跳转本身靠它完成（写是刚需，就算没有前端也照样执行）；
  • 前端展示：React 轮询快照显示状态、进度、子问题结果、错误；
  • Research 的恢复数据源：子问题结果与证据存在快照的 worker_checkpoints，retry 复用；
  • Deep Document 的恢复入口摘要：快照里的 deep_agent_checkpoint 字段只写展示信息（active / resumable / released、resume_count、保留期限），不复制 candidates、SHA 或 thread_id。

最后一项展开看：前端需要知道"这个失败任务能不能恢复"来决定是否显示恢复按钮，但 ACL 指纹、源文件 SHA、thread_id 这些内部安全数据不应发给浏览器。于是 _set_checkpoint_summary()（deep_document_agent.py L1649-1674）把结论翻译成三个可展示状态写进快照：

摘要值含义前端行为
active任务正在执行不显示恢复按钮
resumable失败但现场已保留，可恢复显示"恢复"按钮
released终态已清理不显示恢复按钮

完整时间线：执行失败 → RuntimeRecord 标 failed（内部事实）→ 摘要写 resumable → save() 落库 → React 轮询到 resumable 显示恢复按钮 → 用户点击 → 服务端才去查 RuntimeRecord + Saver 做三道校验。页面只消费"结论"，校验资格是服务端在点击之后做的事。

JSON / Markdown 现在是什么角色？ AgentTaskPlanStore 从 PostgreSQL 读取和保存业务事实；AgentTaskPlanExportStore 只生成可重建的人工审查导出物。导出失败只记录 warning，不能回滚已经提交的数据库事实，也不能被业务读取当作真相。

5.6 这一章背什么

  • 四张表各有唯一职责：任务事实与租约（plans）、幂等命令（commands）、集群容量槽（slots）、Deep Document 恢复登记（runtime）；
  • 三条关系：任务拥有至多一条 Runtime、收到零到多条命令、临时占用零或一个容量槽——前两条由数据库外键强制，第三条是"使用关系"而非"归属关系"；
  • Runtime 表是 checkpoint 恢复前的安全门：ACL 指纹、源文档哈希、checkpoint 存在性三道校验全过才恢复；它只存指针与最小事实，checkpoint 本体在 PostgresSaver 加密表里；
  • 四张表共同回答四个问题：任务什么样（plans）、这个幂等键办过吗（commands）、还有名额吗（slots）、能安全恢复吗（runtime）——正是第 4 章"一口气三件事"加"崩溃恢复"的全部落点。
Chapter 6 · 状态名必须表达业务含义

完整状态机：确认前“准备材料”，确认后才“执行副作用”

6.1 为什么状态机存在：它不是给前端看的标签，而是给 SQL 用的条件

先接回前两章：第 4 章的条件 UPDATE 里有一个 WHERE 条件是 status.in_(allowed_statuses)，第 5 章的主表里有一个 status 字段。状态机就是这两个东西的取值规则——它回答：status 允许取哪些值、从哪个值能变到哪个值。为什么这套规则值得单独一章？因为一句话写错，后果不是页面显示错，而是某条条件 UPDATE 可能放行一个非法转换，例如：

  • waiting_confirmation → completed：用户还没点确认，任务就"完成"了——真实副作用（写文件、发 MR、写 ES/Milvus）会在没有人工授权的情况下发生；
  • cancelled → executing_confirmed：已取消的任务又被执行——旧执行者"复活"，用户取消的事实被推翻。

所以状态机的本质是：把"哪些转换合法"编码成数据库可执行的条件。下面先看完整状态图，再看这张图如何变成代码。

先分清一件事：状态机管"转换合不合法"，不是管"多 Worker 抢着写"

状态机回答的问题是：从一个状态能不能变到另一个状态。判断依据是业务规则，与"几个人在抢"无关——上面两个非法转换的例子，单机单 Worker、没有任何并发时同样会发生。就算全世界只有一个执行者，把状态机删掉，代码照样可能把 waiting_confirmation 直接写成 completed。所以状态机的动机是业务正确性，不是并发控制。

防"多个 Worker 争抢覆盖状态"的，是 save_snapshot WHERE 里的另外几个条件。把六个条件按"防什么"分两组看：

WHERE 条件防什么没有并发也会发生吗属于哪个机制
record_version == 期望值旧快照覆盖新快照❌ 需要并发并发控制（租约 / fence / CAS，见第 7 章）
lease_owner == 我执行权已被领走❌ 需要并发
lease_fence_token == 我的代际旧一代执行者复活写数据❌ 需要并发
lease_until > now()拿过期租约写❌ 需要并发
status IN (允许的来源)非法状态跳转✅ 单机也会发生状态机（业务规则）

为什么会把两者混在一起：因为它们共用同一条 UPDATE——状态机字典被翻译成 WHERE 里的 status.in(...)，和版本、租约、fence 条件并列，执行时一起判断、命中 0 行时一起抛同一个 VersionConflictError。机制上合并了，动机上仍是两回事。

一句话总结：状态机 = 业务规则进数据库，保证"转换本身合法"（有没有并发都成立）；租约 / fence / CAS = 并发控制，保证"写的人有资格、写的内容不过期"（只在并发时才有意义）。这两个动机合起来，才是 save_snapshot 带六个条件的完整原因——四条管资格，一条管合法性，一条管目标行。

读这套卡片抓住四点：

  • 主干链：created → preparing → waiting → executing → 终态，confirm 是进入 executing 的唯一入口；
  • cancelled 卡：进入来源一列有 5 个状态——这正是字典里 CANCELLED 键的全部成员，而"可去往"为空，取消是单向的；
  • failed 卡：可去往一列有两条 retry 回路（回 preparing 或回 executing），靠 failure_phase 记住失败发生在哪一阶段；
  • 两个"自己"：preparing 和 executing 的进入来源里都有"自己"——执行过程中每完成一个子阶段就保存一次快照，状态不变、版本 +1，这条边就是为反复保存开的。

6.2 八个状态在业务上各自做什么

状态系统正在做什么允许真实副作用吗为什么需要单独存在
createdTaskPlan 事实行刚创建。不允许稳定创建点；与尚未开始准备区分。
preparing_confirmation生成预览、dry-run、Supervisor 决策和确认材料。不允许告诉用户“系统在准备确认内容”，不是在执行已确认动作。

executing_confirmed用户已经确认，业务执行器正在工作。允许，但仍需权限、fence 和状态复核把人工授权后的执行阶段变成可审计事实。

它被执行很多次，不是只在任务结束时一次

上面的箭头每一步都是一次 save；执行途中每完成一个子阶段，还会状态不变地再 save 一次（快照内容更新、版本号 +1）——这正是 6.1 卡片里两个"自己→自己"边存在的意义。这样设计有两个目的：

  • 进度可见：任务跑几分钟，如果只在结束时写一次，前端轮询看到的永远是旧状态；每完成一段就写，前端和崩溃恢复才能看到"跑到哪了"；
  • 每段都是完整快照：save 传的是 plan.model_dump() 整个对象，不是"只改哪几个字段"的部分更新——数据库里的 snapshot_json 永远是一个自洽的完整任务状态，恢复时拿来就能直接用。

VALUES 部分就是它做的三件事：改状态、整个快照替换、版本号 +1。六个 WHERE 条件的含义是"只有当数据库那一行还是我以为的那个样子时才允许改，否则一行都不改"：

条件防什么什么时候会失败
② record_version别人抢先改过快照两个执行者同时写
③ lease_owner执行权已被领走租约过期后 B 接手了
④ lease_fence_token旧一代执行者"复活"写数据A 崩溃→B 接手（fence+1）→A 恢复想写
⑤ lease_until拿过期租约写心跳断了、租约超时
⑥ status.in(...)非法状态跳转想从 waiting_confirmation 直接写 completed

一个完整场景：执行者 A 与用户 cancel 的竞争

把上面的机制放进一个具体时间线——执行者 A 正在跑任务，用户中途点了 cancel：

时刻发生什么数据库里的值
t1A 领取租约，lease 句柄记录当前值version=7, fence=12, status=executing_confirmed
t2A 保存进度若干次（save 命中，RETURNING 把新版本写回句柄）version 递增到 10
t3用户 cancel：cancel_atomic 改行 + fence+1version=11, fence=13, status=cancelled
t4A 跑完，想写 completed，执行 saveUPDATE 的 WHERE 比对：version 10≠11 ❌、fence 12≠13 ❌、status 不是 executing ❌
t5命中 0 行 → 抛 VersionConflictError → A 的写入作废保持 version=11, status=cancelled

关键结论：A 在 t4 的失败不是因为它主动检查了数据库——它甚至不知道 cancel 发生过。是 UPDATE 的 WHERE 条件替它完成了检查，检查与写入在同一条 SQL 里原子完成。这正是第 2 章 TOCTOU（先查后写会被插队）的工程级解法：不先查再写，而是把检查条件并进写操作本身。

一句话总结：save_snapshot = "把内存里改好的 plan 对象写回数据库那一行"。它做三件事（改状态、替换快照、版本 +1），但只有当数据库行还是"我以为的样子"（版本、执行权、代际、租约、状态跳转都合法）时才写，否则一行不改并报错。

6.7 两套状态机：TaskPlan 与 Command 各管各的

TaskPlan 状态与 Command 状态是两套不同状态机 TaskPlan 不再使用含糊的 running；但命令表仍然需要 running / succeeded / failed / rejected / cancelled，因为它描述的是“一次 HTTP 控制命令的处理情况”，不是整个业务任务生命周期。不能因为 TaskPlan 删除了 running，就把命令表的 running 一并删除。

两套状态机的对应关系，可以在第 4 章的场景里对出来：一条 confirm 命令从 running 走到 succeeded 的期间，TaskPlan 可能依次走过 waiting_confirmation → executing_confirmed → completed。命令状态回答"这次 HTTP 请求办得怎么样"，任务状态回答"业务走到哪一步"——它们互相引用但不共享取值。

6.8 这一章背什么

  • 状态机的分界线是人工 confirm：确认前只准备材料（preparing/waiting），确认后才执行副作用（executing_confirmed）；
  • 状态机 = 一张规则字典（目标→允许来源），图上的每条箭头都是字典里的一个集合成员；
  • 规则有两层强制：save_snapshot 把来源集合写进 UPDATE 的 WHERE（管转换合法性），数据库 CheckConstraint 管取值合法性；
  • retry 靠 failure_phase 记住失败阶段，准备期失败回 preparing、执行期失败回 executing；TaskPlan 与 Command 是两套独立状态机。

为什么不能只上一个“更大的锁”

7.1 进程内快速锁：减少数据库竞争，不承担跨进程真相

_TaskPlanLockRegistry 维护 task_plan_id → asyncio.Lock。_guard 只保护这个字典的创建和删除；每个 TaskPlan 有自己的锁，因此不同任务仍可并行。

当前源码核心 · _TaskPlanLockRegistry.hold()
async with self._guard:
    lock = self._locks.setdefault(task_plan_id, asyncio.Lock())
    if lock.locked():
        raise AgentTaskPlanBusyError("Agent task plan 当前仍在执行")
    await lock.acquire()

    yield
finally:
    async with self._guard:
        lock.release()

它选择 fail-fast 而不是排队：第二个同进程请求立即得到 409。因为排队后继续执行很可能把一次用户重复点击变成第二次业务执行。

7.2 数据库租约：有过期时间的跨进程执行权

租约不是永远持有的锁，而是“在 lease_until 之前，数据库承认 owner 有执行资格”。领取 SQL 只有在状态允许且旧租约为空或已过期时才成功。当前默认租约 90 秒，心跳 20 秒；Settings 强制心跳间隔小于租约时长的三分之一。

当前源码核心 · begin_operation() 的 TaskPlan 领取条件
UPDATE agent_task_plans
SET lease_owner = :worker_id,
    lease_until = now() + interval '90 seconds',
    lease_fence_token = lease_fence_token + 1,
    active_operation = :operation
WHERE task_plan_id = :task_plan_id
  AND status IN (:allowed_statuses)
  AND (lease_until IS NULL OR lease_until <= now())
RETURNING lease_fence_token, record_version;

这里的 SQL 是依据当前 ORM 逻辑改写的教学等价形式。真正实现使用 SQLAlchemy update(...).where(...).returning(...)。

为什么租约还需要一个"心跳"——从租约的过期设计说起

租约（lease）有有效期，这个设计解决了一个问题：执行者崩溃后，任务不能永远锁死。执行者 A 领取租约 90 秒后，就算 A 的进程突然消失，数据库上的租约也会自动过期，别的执行者可以接手。

但这带来了一个矛盾：一个真实任务往往要跑几分钟到十几分钟，而租约只有 90 秒。如果执行者活着、任务还没跑完，租约却到期了，别的执行者就会合法接手——同一个任务出现两个执行者。解决这个矛盾的办法就是心跳（heartbeat）：

心跳 = 执行者在租约到期之前，定期去数据库把 lease_until 往后推。每推一次，就相当于对数据库说"我还活着，这个租约继续归我，再给我 90 秒"。

当前配置（core/config.py L458-471）：租约 90 秒，心跳间隔 20 秒。两者必须满足一个硬性比例——配置文件末尾的校验器（L840-842）：

当前源码核心 · 心跳间隔必须小于租约三分之一（config.py L840-842）
if self.agent_task_heartbeat_seconds * 3 >= self.agent_task_lease_seconds:
    raise ValueError(
        "AGENT_TASK_HEARTBEAT_SECONDS 必须小于 AGENT_TASK_LEASE_SECONDS 的三分之一"

为什么是"小于三分之一"而不是"小于就行"？为了容错：即使某次心跳因为网络抖动失败，还有两次补推的机会，租约不会立刻过期。20 × 3 = 60 < 90，意味着至少能容忍连续两次心跳失败。

心跳任务在哪里启动：领取租约成功后立刻创建

心跳的启动点在 AgentTaskLeaseManager.hold()（agent_task_lease_manager.py L90-91）：

        await heartbeat                               # 等它真正退出

心跳是一个独立的 asyncio 协程，与业务执行并行运行（第 2 章学过：它们在同一事件循环里轮流执行）。业务执行期间它每 20 秒醒来一次续租；业务结束时通过 stop 事件通知它退出。

读懂这段代码前，先补三个 asyncio 概念和一个 Python 机制

概念一：asyncio.Event 是一个"信号"，只有两种状态：未设置（初始）和已设置。配套两个方法：event.set() 点亮信号；await event.wait() 挂起等待，直到信号被点亮才继续。

概念二：asyncio.create_task(协程) 把协程注册到后台运行，立即返回一个 Task 对象，协程自己在后台跑。之后用 task.cancel() 取消它、await task 等它真正退出。

概念三：asyncio.wait(任务集合, timeout=秒, return_when=FIRST_COMPLETED) 同时等多个任务，返回两个集合：done（已完成的任务）和 pending（未完成的任务）。三种结局：某任务完成 → done 非空；超时 → done 为空；配合 FIRST_COMPLETED 表示"有一个完成就立刻返回"。

机制四：yield + @asynccontextmanager 的"进入/退出"模式。先用最小例子理解 yield 本身：

教学示例 · 裸生成器：yield = 暂停并把值交出去
def demo():
    print("第一段")

核心：yield 是"暂停 + 交出值"，生成器停在那儿，外面继续跑；外面再次驱动它，它才接着跑。

而 with 语句的执行顺序固定是：__enter__() → with 块内代码 → __exit__()，且 as x 的 x = __enter__() 的返回值。@asynccontextmanager 把这两者拼起来——把一个带 yield 的生成器函数自动转换成语境管理器：

教学示例 · yield 前后 = 进入和退出

@contextmanager
def 管理器():
    print("进入")              # yield 之前 = __enter__()
    yield "交给 with 块的值"   # yield 的值 = as x 的 x
    print("退出")              # yield 之后 = __exit__()

with 管理器() as x:
    print("业务代码，拿到", x)
print("with 结束")
# 输出：进入 → 业务代码，拿到 交给 with 块的值 → 退出 → with 结束

对照表：yield 之前的代码 = __enter__()；yield 交出的值 = as x 的 x；yield 之后的代码 = __exit__()。执行顺序就是"进入（yield 前）→ with 块 → 退出（yield 后）"——这就是"执行到 yield 会回到 with 块内业务代码"的原因：yield 是进入阶段和 with 块之间的分界线。

7.3 fencing token：租约过期后，让旧执行者永久失去写权

只靠到期时间仍有一个危险：Worker A 暂停很久，租约过期；Worker B 接手并执行；随后 A 又恢复。A 的本地代码可能仍以为自己在运行。fencing token 给每次领取发一个单调递增的“代际编号”。

第一代

A 领取，数据库把 fence 从 0 改为 1。A 的所有写入必须携带 token=1。

第二代

A 过期，B 领取，数据库把 fence 从 1 改为 2。B 携带 token=2。

旧人复活

A 用 token=1 保存；WHERE 要求当前 token=1，但数据库已经是 2，所以 rowcount=0。

租约回答“现在是否到期”，fencing 回答“你属于哪一代” 时间可能向前走，进程可能暂停又恢复；代际编号一旦落后就永远落后。因此旧 Worker 无法因为本地时钟、网络延迟或事件循环恢复而重新获得旧权限。

7.4 原子 CAS：防止同一代执行者拿旧快照覆盖新快照

先回答一个命名问题：为什么把一行 SQL 叫做 CAS？

如果学过线程同步，会先想到自旋锁里的 CAS 指令。两者"长得完全不一样"，但共享同一个本质：检查与写入合成一个原子动作。自旋只是内存场景下的配套重试策略，不是 CAS 的本义。

把 CAS 三要素在两处对照：

CAS 要素硬件自旋锁里数据库 UPDATE 里
Compare（比较）&lock == 0WHERE record_version = :expected AND lease_owner = :owner ...
Swap（交换）写入 1SET record_version = record_version + 1, snapshot_json = ...
原子性来源CPU 指令本身数据库行锁（一条 UPDATE 在数据库中不可分割）
失败后自旋重试（while 循环再试）不重试：命中 0 行，抛异常交给调用方

为什么数据库场景不自旋，三个理由：

  • 临界区太长：自旋锁保护的临界区是纳秒级；一次 save_snapshot 对应的业务"临界区"是分钟级，失败后原地重试等于烧 CPU 干等；
  • 失败原因是持久的：硬件锁失败 = "别人正拿着，马上会放"；数据库 CAS 失败 = "版本已被覆盖 / 执行权已易主 / 已取消"——这些事实不会自己变回来，重试毫无意义，正确动作是放弃并报告（fail-fast）；
  • 并发方可能已死：数据库场景里对手可能是崩溃的进程，自旋重试 = 等一个死人；数据库靠租约过期自动解锁，新执行者一次 CAS 成功接手。

顺带理清名称关系：数据库 CAS 和"乐观锁"是同一件事的两个名字——叫 CAS 强调机制（WHERE 里的版本比较 + 原子写入），叫乐观锁强调策略（乐观地假设没人抢，写失败再处理；对比悲观锁 SELECT FOR UPDATE 先锁住再干）。工程里两种都在用：save_snapshot 用 CAS/乐观锁，cancel_atomic 用 SELECT FOR UPDATE 悲观锁。本质上都是第 2 章 TOCTOU 解法——"检查与写入一步完成"——在不同介质上的实现。

这章要解决的问题：fence 挡不住的"旧内容覆盖新内容"

先定位问题场景，再引入工具。fence（7.3）挡的是上一代执行者复活。但更隐蔽的丢失更新发生在同一代执行者内部：

时刻发生什么数据库 record_version
t1执行者 A 读快照到内存对象 plan_x= 7（A 读到的是第 7 版）
t2A 继续执行（几分钟），期间另一写入路径把行更新了一次（如深层组件保存进度）= 8
t3A 跑完，用手里基于第 7 版的 plan_x 调用 save若无条件 UPDATE → 第 8 版被第 7 版内容整体覆盖 ❌

关键点：fence 挡不住这个场景——A 仍是合法的"这一代"执行者，fence 没变。所以需要第二个尺度：快照版本号。

工具：record_version 是"这一行被写过多少次"

每次 save 成功，record_version + 1。这个数字的含义就是"行被修改的次数"：你手里的 plan_x 是第 7 次写入之后的内容，如果数据库已写到第 8 次，你手里的就是旧内容——旧内容无权覆盖新内容。

机制：光有版本号不够，比较和写入必须一步完成（这才是 CAS 的主旨）

错误做法是"先查后写"——第 2 章的 TOCTOU：

教学示例 · 错误做法：检查与写入是两个步骤
# ❌ 检查之后、写入之前，别人可能已经写成 8
if 数据库当前版本 == 7:      # 步骤 1：检查
    UPDATE ... 无条件写入     # 步骤 2：写入（中间可以被插队）

正确做法是把"检查"塞进写语句的 WHERE，让数据库原子执行——比较与写入之间没有任何空隙：

教学示例 · 正确做法：比较写进 WHERE，一步完成
UPDATE ...
SET record_version = record_version + 1, ...
WHERE record_version = 7        -- 比较：不是 7 就一行都不改

两种结果：命中 1 行 → 版本还是 7，写入成功、版本变 8；命中 0 行 → 版本已不是 7，什么都不写、抛异常——旧快照没有覆盖任何东西。Compare（WHERE 比较版本）+ Swap（SET 写新值）合成一个原子动作，这就是"原子 CAS"这个章节名的完整含义——record_version 只是 Compare 用的那个数字，CAS 才是主角。

与 fence 的分工（一句话记牢）

机制挡谁用的数字回答的问题
fencing token上一代执行者lease_fence_token"你还是这一任吗？"
record_version CAS同一代内的旧快照record_version"你手里的内容还是最新的吗？"

两个问题都需要问——这正是 save_snapshot 的 WHERE 里同时有 lease_fence_token = ... 和 record_version = ... 的原因。所以 7.4 想表达的完整版是：在"执行者合法性"（fence）之外，还需要第二道防线防止"旧内容覆盖新内容"（丢失更新）；做法是给行一个单调递增的版本号，并把版本比较塞进 UPDATE 的 WHERE——让检查与写入一步完成（CAS）。这也是第 2 章 TOCTOU、第 4 章条件 UPDATE、6.4 save_snapshot 三条学习线在"快照写入"这个点上的汇合。

fencing 防旧执行者，record_version 防旧快照。两者解决的问题不同。当前 save_snapshot() 一次性校验五件事：

  1. task_plan_id 是目标任务；
  2. record_version 等于租约句柄记录的版本；
  3. lease_owner 等于当前 Worker；
  4. lease_fence_token 等于当前代际且租约未过期；

7.5 幂等命令：网络重试不等于第二次业务操作

问题场景：一次点击，两次到达

用户在网页上点"确认"，请求发出后网络超时，用户没看到结果，于是又点一次（或客户端自动重试）。服务器收到两个"确认"请求——如果两个都当真，任务就执行两遍。7.5 要解决的问题：网络重试产生的重复请求，不能让服务器重复执行。

解法：给每次用户动作一个唯一编号，重试时复用同一个编号

第 6 站：重复请求按老命令状态分五种回应

已有命令状态同 key + 同 hash 的处理原因
succeeded返回 TaskPlanCommandReplay，重放原 response_json。动作已经成功，不再执行副作用。

t4请求③ header: K-001（又重试）INSERT 冲突 → 查出 K-001 是 succeeded → 把 t3 存的 response 原样返回（不重新执行）

三次请求、一个编号：一次执行、一次 409、一次重放。key 的作用就是这三步——让服务器能分辨"这是我见过的那个动作"。这也是"幂等"的含义：同一个动作做一次和做一百次，效果一样。

幂等命令不等于外部网络副作用“恰好一次” 如果请求已经发到 GitLab，但响应在网络中丢失，数据库无法凭空知道 GitLab 是否成功。命令幂等只能防控制入口重复执行；真正的外部副作用还必须使用稳定业务幂等身份，例如稳定 MR 身份、唯一约束或目标系统提供的幂等键。

7.6 全局容量槽：数据库版集群信号量

问题场景：为什么需要"全局限量"

Research 和 Deep Document 是重任务：单任务要跑几分钟、调用几十次模型、占连接池和检索资源。必须限制"整个集群同时最多跑几个"。当前配置：Research 全局 2 个、Document 全局 1 个（压测方案 §2.3）。

为什么 Python 进程内的 asyncio.Semaphore(2) 不够用？回忆第 2 章：每个 Worker 是独立进程，各有一份内存。Semaphore(2) 是进程内对象，四 Worker 部署下会变成 4 个进程 × 每进程 2 个 = 全局最多 8 个名额，不是全局 2。所以限量必须放在所有 Worker 共享的地方——数据库。

解法：一张"车位表"，车位是预先创建好的固定行

第 5 章的 agent_task_capacity_slots 表就是这个"全局信号量"。关键设计：槽位不是"有任务才创建"，而是启动时预创建好的固定行（ensure_capacity_slots()，repository L68-80）：

当前源码核心 · 启动时预创建固定槽位（repository L68-80 节选）
async def ensure_capacity_slots(self, *, workload_type: str, count: int) -> None:
    values = [
        {"workload_type": workload_type, "slot_no": slot_no}
        for slot_no in range(1, count + 1)          # research → 1,2；document → 1
    ]
    ...
    pg_insert(AgentTaskCapacitySlotTable)

所以数据库里常年躺着这几行：(research, 1)、(research, 2)、(document, 1)。每行就是一个"名额"。任务执行期间占用它，结束后归还它——行不会被删除，只改行的租约字段。

代码怎么读：列表不是"存进数据库的数组"

上面的 values 是一个 Python 列表（内存里的中间容器），里面装着 2 个字典。假设 workload_type="research", count=2，它算出的内容是：

    {"workload_type": "research", "slot_no": 1},
    {"workload_type": "research", "slot_no": 2},

关键点：数组只存在于 Python 内存里，数据库里没有"数组"概念——数据永远是行。SQLAlchemy 看到"列表里有 2 个字典"，就自动展开成一条多行 INSERT，最终落库的是两行独立记录。以后看到 .values(一个列表) 的写法，记住这个展开规则。

槽位数量来自配置，工程关闭后怎么办？

数量来自配置：槽的数量不写死在代码里，来自 Settings——AGENT_RESEARCH_GLOBAL_CONCURRENCY=2 生成 (research,1)(research,2)，AGENT_DOCUMENT_GLOBAL_CONCURRENCY=1 生成 (document,1)。改配置重启后按新数量补建。

工程关闭后槽行不删除，分三种情况：

  • 正常关闭：槽行原样留在数据库，全部空闲。下次启动 ensure_capacity_slots() 发现已存在 → on_conflict_do_nothing 跳过——不重复创建、不删除、不重置；
  • 停机时还有任务在跑：被占的槽挂着死进程的 lease_owner，没有清理代码执行——但槽有自己的租约，90 秒后 lease_until 过期，下次新请求领取时 WHERE 条件 lease_until <= now() 判定"已过期 = 空闲"直接领走。这正是"为什么槽也要配租约"的答案：进程可以随时死，租约到期就是自动解锁，不管死得干不干净；
  • 改小配置不会自动删槽：改成 research=1 后，启动只补"还不存在的"，不会删掉 2 号行；但领取时 slot_no <= capacity_limit 条件限制"只允许领 1 号"，2 号行躺表里但永远领不到——不删它也不会超发，因为限额由 SQL 条件强制，不是靠行数。这就是"配置即上限"的设计。

一句话总结：槽表是"启动时按配置预创建、永久保留、靠租约自动解锁"的固定资源表；工程关闭不影响槽行，异常停机占用的槽 90 秒后自动过期，实际限额由 SQL 的 slot_no <= capacity_limit 强制。

槽位行也有自己的租约和代际

每个槽位行带三个字段（第 5 章的表结构）：lease_owner（当前占用者）、lease_until（占用到期时间）、lease_fence_token（第几代占用）。为什么槽也要租约？因为占用者的进程可能崩溃：

  • 崩溃后槽的租约到期（90 秒无心跳）→ 槽自动空闲，别人能领——车位不会永久锁死；
  • 槽的 fence 让"旧占用者复活"时续租/归还都失败——旧人不能动新车位（7.2 学过：心跳同时续 TaskPlan 和槽两行，续的就是这个槽）。

领取动作：在 begin_operation 里，它是第三件事

回顾第 4 章"一口气三件事"：①幂等命令落库 → ②TaskPlan 租约领取 → ③容量槽领取。第③步的 SQL（repository L259-272）：

当前源码等价 SQL · 领取一个全局容量槽
SELECT *
FROM agent_task_capacity_slots
WHERE workload_type = :workload_type        -- 车型要对（research 还是 document）
  AND slot_no <= :capacity_limit            -- 只找限定的槽号（如 1、2）
  AND (lease_until IS NULL OR lease_until <= now())   -- 槽要空闲（没人占或已过期）
ORDER BY slot_no                            -- 从 1 号开始找
FOR UPDATE SKIP LOCKED                      -- 关键：跳过正被其他事务锁住的行
LIMIT 1;

SKIP LOCKED 的含义：多个请求同时来抢仅有的 2 个槽时，先到的事务会把看中的槽行"锁住"（FOR UPDATE）；后来的事务看到这行被锁，不等它解锁，直接跳过找下一个空槽——不排队、不死锁。这正是三个 confirm 并发时"2 个领到槽、1 个领不到"的机制：两个赢家各自锁住一个槽行，第三个事务跳过两个被锁的行，找不到任何行。

注意区分两个"空"：WHERE 里的 lease_until IS NULL OR lease_until <= now() 判断的是业务上未被占用；SKIP LOCKED 跳过的是正被其他事务锁住、尚未提交的行——两者叠加，才能保证并发下既不超发、也不排队。

领到之后：槽行被写入占用信息

找到空槽后（repository L295-344）：槽行写入 lease_owner / lease_until（90 秒）/ lease_fence_token +1 / task_plan_id；主表行回写 capacity_workload_type / capacity_slot_no（记住自己占的是哪个槽，归还时按号还）。执行者手里得到完整句柄：TaskPlan 租约 + 容量槽号 + 槽的 fence。

领不到：归还刚拿的租约，命令标 rejected，返回 429

一个空槽都没有时（repository L273-294 + L348-352）：

  1. 把刚才第②步领到的 TaskPlan 租约还掉（否则任务占着租约却没资格执行）；
  2. 命令标 rejected，错误码 AGENT_CAPACITY_EXCEEDED；
  3. 向客户端抛 429，带 retry_after_seconds（告诉前端"满了，等 90 秒再试"）。

429 是"拒绝"不是"排队"——这是本方案的明确选择：宁可让用户稍后重试，也不在服务端堆积长队列（堆积的长任务反而会拖垮所有在线请求）。

归还：终态收尾时按号释放

任务结束后，finish_success() / finish_failure() 把槽行清空（第 6 章读过 L465-481）：lease_owner / lease_until / task_plan_id 置空——槽行回到"空闲"，等待下一个任务。而心跳（7.2）在任务运行期间每 20 秒同时续 TaskPlan 和槽两行，保证长任务不会中途丢车位。

7.7 取消必胜：cancel 不等正在运行的锁

为什么 cancel 特殊：它是七个机制里唯一"要和正在跑的任务正面对抗"的操作

前面六个机制都在防"重复/越权/过期"，cancel 却是要打断。对比三个控制操作在"任务正在执行中"时的行为：

操作任务正在执行中时行为
confirm第二个 confirm 到来被进程内锁/数据库租约挡住 → 409"有人在办"（等不了就拒）
retry同上同样被挡
cancel任务正在跑，用户要取消必须立刻写入"已取消"事实，不能让执行者继续干

如果 cancel 也像 confirm 一样先去拿 _TASK_PLAN_LOCKS 进程内锁（第 4 章），会发生互等死锁：cancel 在等任务放锁，任务在等看到 CANCELLED 信号才停——永远取消不掉。所以 cancel 的第一条特殊设计（executor L232 注释原文）：cancel 故意不进入进程内锁，跳过排队，直接去数据库原子改写状态。

为什么"必胜"必须靠 fence + 状态机：它要对抗一个正在写库的执行者

正在执行的任务每 20 秒心跳续租、每完成一段就 save 快照。如果 cancel 只是"改一下 status"，执行者下一次 save 可能把它覆盖回去——取消就没意义了。cancel 的"必胜"是把 7.3 和 6 章的武器一次打出去：

  • lease_fence_token + 1：执行者的所有后续写入（save、续租）都要求 fence 还是自己的旧值——现在变了，全部命中 0 行，执行者失去写权（7.3 的 fencing 武器）；
  • record_version + 1 + status=cancelled：执行者的 save 还要求"来源状态合法"——cancelled 不是任何"继续执行"的合法来源（第 6 章状态机），同样命中 0 行（7.4 的 CAS 武器）。

执行者不会立刻停，但它从此写不进任何东西；它会在下一个心跳/保存失败时意识到"我输了"，收敛退出。

为什么用 SELECT FOR UPDATE（悲观锁），而不是 CAS

cancel 要同时改三张表（任务行、容量槽行、其他命令行），而且必须先读旧值（旧租约 owner、旧槽号）才能正确归还槽。这种"读一行 → 根据读到的内容改多处"的流程，单条条件 UPDATE（CAS）不够用——必须先把任务行锁住，防止读和改之间别人抢先（repository L605-609）。这就是 7.4 提到的"工程里两种都在用"：快照写入用乐观 CAS，cancel 用悲观锁。

Chapter 11 · 不背术语，用竞态验证设计

四种最值得亲手推演的并发场景

场景 A：两个 Worker 同时 confirm 同一 TaskPlan

W1、W2 的进程内锁都空闲，因此两者都会进入 Repository。数据库的条件 UPDATE 只能让一个事务把空闲租约改为自己的 owner。赢家继续领取容量槽；输家 UPDATE 返回 0 行，命令被标记 rejected，并得到 409 BUSY。

防线：TaskPlan 租约。不应依赖：进程内锁。已观察证据：跨进程测试只有 1 acquired + 1 BUSY；四 Worker 20 请求只有 1 个业务执行者。

场景 B：Worker A 停顿，租约过期，Worker B 接手

A 持有 fence=5 后暂停。租约过期，B 成功领取并得到 fence=6。A 恢复后本地代码还在，但续租、TaskPlan 保存、Runtime 保存和终态提交都要求数据库 fence=5；数据库已经是 6，因此 A 只能收到 lease-lost/version-conflict，不能覆盖 B。

防线：lease expiry + fencing token。单有租约到期而没有 fence 条件，A 仍可能用旧内存结果写回。

场景 C：cancel 与 completed 几乎同时发生

cancel 用行锁把 status 改为 cancelled，同时 record_version+1、fence+1 并清空租约。旧 runner 保存 completed 时，version/fence/allowed source status 都不再匹配。即使 runner 已经返回业务结果，finish_success() 也会失败并重读数据库；发现 cancelled 后以取消结果为准。

防线：原子 cancel + fence invalidation + 单调状态机 + finish_success 二次收敛。

场景 D：三个 Research confirm 同时到达，但全局容量是 2

三个请求操作三个不同 TaskPlan，因此任务租约都可能成功。但容量表只有 research slot 1 和 2。前两个事务各锁定一个空闲槽；第三个找不到槽，释放自己刚拿到的 TaskPlan 租约，把命令记为 rejected，返回 429 AGENT_CAPACITY_EXCEEDED 和 Retry-After。

防线：容量槽。它解决的是资源过载，不是同任务重复执行。

13.1 深读 AgentTaskLeaseManager.hold()

它拥有的问题：把一次控制请求从“普通协程”变成“持有数据库权威租约、接受心跳监督的执行链”。

  • 输入：task_plan_id、operation、idempotency_key、请求 payload、允许状态和 workload 类型。payload 与 key 属于请求事实；允许状态和容量上限属于服务端策略。
  • 关键局部变量：acquired 可能是新 TaskPlanLease，也可能是已成功命令的 TaskPlanCommandReplay。
  • 分支：Replay 直接 yield 后返回；Lease 则创建 stop Event、启动 heartbeat、绑定 ContextVar。
  • 失败传播：心跳异常把 lease.lost 置位；主业务在安全边界调用 assert_active() 失败。
  • 清理：finally 必定停止并取消心跳，避免请求结束后后台协程继续续租。

13.2 深读 AgentTaskExecutor._run_with_database_lease()

它拥有的问题：Research 与 Document 的业务完全不同，但领取、重放、心跳、权威重读、成功释放和失败收尾应使用同一套控制协议。

  • 先进入 LeaseManager；Replay 时从 response_json 还原 Plan，不运行 runner。
  • 拿到 lease 后重新从数据库 load，避免使用 API 层较早读取的旧对象。
  • 调用专用 runner；业务过程中所有 Store.save 都从 ContextVar 取得同一个 lease。
  • runner 返回后再 assert_active，并先设置 closing 停止心跳，再调用 finish_success。
  • 若 cancel 已经赢得竞态，重读 cancelled 并把它作为权威结果。
  • 其他异常尝试把仍处于活动状态的 Plan 收敛为 failed，然后 finish_failure 释放资源并保留原异常。

13.3 深读 DeepDocumentRuntime.update_record()

14.2 仍需理解的残余边界

租约不是 exactly-once

数据库能阻止旧 Worker 保存本地事实，但对已经发出的外部网络请求无法撤回。外部副作用仍需业务幂等。

checkpoint 与业务事实不是一张表

LangGraph 官方 Saver 写 checkpoint，业务 RuntimeRecord 通过 Repository CAS；极窄的 checkpoint 写窗口仍要依靠执行边界与恢复规则处理。

容量数字不是性能承诺

Research=2、Document=1 是保守熔断值。只有完整压测的成功率、P95、连接池和成本数据才能形成容量承诺。

数据库成为关键依赖

PostgreSQL 不可用时不能降级到本地 JSON 继续执行，否则会重新引入分裂事实。

14.3 常见误区

误解正确理解
“有 asyncio.Lock 就线程安全了。”先问作用域。它只保护创建它的进程内协程。
“数据库事务等于分布式锁。”事务只是边界；必须有正确的条件 UPDATE、行锁、过期和 owner/fence 条件。
“有 lease_owner 就够了。”owner 字符串可能被旧进程继续持有；需要 expiry 和单调 fence。
“有 fence 就不需要 version。”同一代内仍可能有旧快照；version 负责快照顺序。
“幂等键每次重试都换一个。”同一次用户动作必须复用同一个 key；新点击才生成新 key。
“cancel 应该先拿执行锁。”这会让取消信号等任务结束后才写入。cancel 必须能立即使 fence 失效。
“原子写 JSON 就不会覆盖。”它只保证文件不残缺，不保证旧业务状态不能覆盖新终态。
“19 个 409 说明整个业务压测通过。”它只证明同 TaskPlan 互斥；不证明 Research/Document 质量和 15 人尾延迟。
Chapter 17 · 把“看懂”变成“会判断”

四组练习：不改生产代码也能建立并发直觉

练习 1：纸面模拟 CAS

  1. 在纸上写数据库：owner=A、fence=3、version=8、status=executing_confirmed。
  2. 让 Writer A 和 A2 都复制这四个值。
  3. A 先保存并把 version 改成 9。
  4. 问：A2 的 WHERE 中哪个条件失败？答案是 version=8。
  5. 再让 cancel 把 fence 改成 4、status 改成 cancelled。问：旧 Writer 至少有几个条件失败？

练习 2：判断每种机制负责谁

同一 HTTP 请求因网络超时重发，应该由谁处理？
Idempotency-Key + command 表。若第一次已成功就重放；仍运行就 BUSY；孤儿/失败/拒绝按规则复活。它不应通过 TaskPlan version 猜测是不是重复请求。
Worker 暂停两分钟后恢复，应该由谁拦截？
lease expiry 允许新 Worker 接手，fencing token 让旧 Worker 的续租、保存和终态提交全部失效。
不同 TaskPlan 同时跑太多导致模型连接池拥塞，应该由谁限制？
全局容量槽。任务租约只限制“同一个任务一个执行者”，不限制不同任务总数。
cancelled 被 completed 覆盖，缺了哪几道保护？
至少缺少原子 cancel、fence invalidation、record_version CAS 和状态来源条件；任何一条单独存在都不如组合条件完整。

练习 3：阅读一次条件 UPDATE

打开 agent_task_plan_repository.py 的 save_snapshot()，逐条给 WHERE 条件标注：

  • 身份条件；
  • 快照新旧条件；
  • 租约持有者条件；

对下面证据分别写一句“能证明”和“不能证明”：

  1. 两个进程结果为 acquired=1、busy=1。
  2. 四 Worker 20 confirm 中 19 个 409、1 个业务执行者。

Chapter 18 · 把复杂方案压缩成稳定心智模型

最后只记住一条“六问法”

未来再遇到多 Worker 任务问题，不要先问“用什么锁”，按顺序问：

1. 事实在哪里？

如果事实只在本地内存或文件，就无法让多个实例统一判断。

2. 谁能领取？

领取必须是数据库原子条件更新，而不是先查再改。

3. 旧人怎么失效？

过期租约允许接手，fencing token 拒绝旧代际。

4. 旧快照怎么拒绝？

record_version CAS + rowcount 判断冲突。

5. 重试怎么去重？

幂等键绑定同一动作和 request_hash，成功时重放。

6. 总容量怎么限制？

共享容量槽，而不是每进程一个 Semaphore。

你现在应该能讲清楚的完整答案 当前工程采用“进程内 task_plan_id 快速锁 + PostgreSQL 权威租约”的双层互斥。控制请求先用幂等命令去重，再通过状态和租约条件原子领取 TaskPlan，同时用 SKIP LOCKED 获取集群容量槽。执行期间心跳同时续租任务和槽位；所有 TaskPlan 与 Runtime 写入都携带 owner、fencing token 和 record_version CAS，状态机把确认前准备与确认后副作用分开。cancel 通过行锁原子写终态并递增 fence，使旧执行者无法覆盖。JSON/Markdown 只做可重建导出，不再承担业务事实。

最终自测

为什么进程内锁仍然保留？
它能让同一 Worker 的重复请求快速 409，减少数据库竞争；但跨进程权威仍由 PostgreSQL 租约承担。
为什么人工确认不能从 waiting_confirmation 直接 completed？
那会把“用户授权”和“真实执行”压成一次不可观察跳转。先持久化 executing_confirmed，执行器和副作用边界才能确定性验证用户已经确认。
为什么同时需要 fence 和 version？
fence 区分执行者代际，version 区分快照新旧。旧代执行者和同代旧快照是两种不同竞态。
当前是否已经证明 10–15 人混合业务可用？
没有。互斥、CAS、容量等一致性机制已有强证据，但正式 10+3+2 在 Research 业务质量、Document 修复后复测和尾延迟方面仍未通过门禁。
